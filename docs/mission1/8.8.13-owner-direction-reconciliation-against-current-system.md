## Purpose

This document checks, without changing anything, how the new Owner direction fits
against the system as it exists today.

It is not a design decision, not a schema proposal, not a database proposal, and not
implementation work. It is a gap-and-risk map.

It exists so the team can discuss the direction against something concrete before any
Requirement or Authorization is considered.

## Owner direction, restated in this document’s terms

The Owner’s direction has four main moving parts.

1. **Separate internal file identity from the name the user sees.**
   - The system can keep stable, internal, non-colliding identities for exports.
   - The displayed name is what humans use to understand and find an item.
   - The real filename is internal system detail.

2. **Library is a management center, not just a file list.**
   - Users should reach a file by what it is: content, product, file type, and the
     displayed name.
   - Users should not need to remember filenames or folder paths.
   - A Library entry can carry what the file is, when it was created, which Content it
     came from, which script version it used, where the real file lives, the file hash,
     and which destinations/uses it has been sent to.

3. **Two consumption paths.**
   - Path A: send from Library directly to a supported destination/channel.
   - Path B: open the real file location from Library, for example Browse/Reveal File.
   - Revealing the file location does not mean the user should edit the stored file
     directly.

4. **Separate Content identity from Export identity.**
   - One Content Project can have many Exports.
   - Each Export can have its own identity and its own file.
   - The same Content Project does not become “multiple files”; the files belong to
     Export records, not directly to Content.

The Owner also added explicit caveats:

- stable names reduce overwrite risk, but that alone is not a complete data-loss
  prevention mechanism
- an export is ready only after file write, hash check, and Library record write all
  succeed
- the direction is to study further; it is not yet a Requirement and not yet system
  approval

## Current system: the parts this task inspected

### Current export file naming

Today, when a FINALIZED project is exported, the exported MP4 is written to:

- `<exportsDir>/<content_id>/<content_id>-v<script_version>.mp4`

In code, that formula lives in `exportProject()` in `app/mvp/content.js`:

- `app/mvp/content.js:1559`
- `app/mvp/content.js:1561`

That means the current filename is determined by:

- the project’s Content ID
- the project’s current script version at export time

So currently, filename identity is partly content identity and partly script-version
identity.

### Current render behavior

The video is rendered by `renderVideo()` in `app/remotion/render.js`.

Relevant current behavior:

- ffmpeg is invoked with `-y` in the render args
- `app/remotion/render.js:318` shows `-y` in the argument construction
- the output path is `options.outFile`, resolved to an absolute path
- `app/remotion/render.js:299` to `app/remotion/render.js:300`

After rendering, `exportProject()` probes the output file back for metadata, and also
writes a still frame. The still frame is also written with ffmpeg `-y`:

- `app/mvp/content.js:1568` to `app/mvp/content.js:1579`

So today, both the MP4 and the still frame can be overwritten in place by the same
name.

### Current export file value capture

After render, `exportProject()` records a rich export object on the project, including:

- `file`
- `filename`
- `bytes`
- `sha256`
- `width`, `height`, `fps`, `duration_s`, `aspect_ratio`
- `codec`, `container`, `encoder`, `font`
- `audio`
- `still`
- `script_version`, `script_checksum`
- `asset_refs`

Reference:

- `app/mvp/content.js:1592` to `app/mvp/content.js:1655` for the export record shape

That is already more than just a filename. The project itself knows a lot about the
export once export completes.

What is important here is that this information currently lives on the project’s export
field, not primarily as a stable cross-export export registry keyed by a stable export
identity.

### Current Content Library behavior

Today there is a Content Library index file.

- path is derived in `contentLibraryFile()`:
  - `app/mvp/content.js:1876` to `app/mvp/content.js:1881`
- default location resolves to:

- the reader tolerates leading `#` comment lines
- `app/mvp/content.js:1883` to `app/mvp/content.js:1903`

When `exportProject()` writes the library:

- it reads the existing index if present
- it removes a prior library entry matching same `id` AND same `filename`
- it pushes a new entry for the current export
- it writes the updated index back

Reference:

- `app/mvp/content.js:1582` to `app/mvp/content.js:1591` for the replace-same-id-and-filename logic
- `app/mvp/content.js:1593` to `app/mvp/content.js:1594` for the write-back

The current library entry fields include:

- `id`
- `filename`
- `sha256`
- `exported_at`
- `width`, `height`, `duration_s`
- `aspect_ratio`
- `status`

So the current Library record is real, but it is fairly compact and keyed by
Content ID plus exported filename.

### Current route/handler picture in the inspected slice

From the inspected code, the MVP content workflow has endpoints for:

- create content project
- edit storyboard / tracks
- QA
- finalize
- export
- publish preparation
- read a library item

It does not, in the inspected slice, include:

- an endpoint whose primary job is “send this export to a configured destination”
- an endpoint whose primary job is “reveal/browse/open the stored file location for the
  user”
- an endpoint whose job is “list exports by stable export identity separate from content
  ID”
- an endpoint for marking an export as sent to a destination with a recorded result

Those absences are implementation facts for this inspected slice, not claims about the
entire repository. Other code may exist outside the inspected slice. This task did not
assert the opposite.

## Reconciliation point by reconciliation point

### 1. Naming and identifying export files

#### What the Owner direction implies

- export files should have stable, system-managed identities
- the user-facing name can differ from the internal filename
- the user finds files by meaning, not by filename pattern

#### What exists today

- export filenames are derived from `content_id` and `script_version`
- the project export record already stores the final `filename` and the full `file` path
- the library store also stores `filename` and `sha256`

#### Where they align

- the system already captures file identity after export
- the system already stores a hash and a path
- the current model already has enough raw material to talk about “what file this is”

#### Where tension exists

- today’s filename is not stable across script-version changes
- today’s filename is not globally unique on its own; it is scoped to a content_id folder
  and to the current script version
- today’s visible identity for an export is largely the project’s content identity plus
  the derived filename, not a separate human-readable export title

#### What is not yet true

- there is no separate, first-class “Export” identity visible to the user in the
  inspected export flow
- there is no separate displayed export name stored for the user to search/filter by

### 2. Writing files and overwrite risk

#### What the Owner direction implies

- exports should be distinguishable so same-name overwrite is less likely to be the
  default expectation
- overwrite risk is reduced but not eliminated by naming alone
- write success, hash success, and record success should be verified before declaring
  readiness

#### What exists today

- ffmpeg is called with `-y`, so a same-name render can overwrite the destination file
- a same-name still frame can also be overwritten
- for the library index, a same `id` and same `filename` entry is replaced before the
  new one is written
- the render path itself verifies that the output file exists after ffmpeg finishes

Reference:

- `app/remotion/render.js:318`
- `app/remotion/render.js:402` to `app/remotion/render.js:406`
- `app/mvp/content.js:1582` to `app/mvp/content.js:1591`

#### Where they align

- the system already records file size and sha256 after render
- the system already checks that the output file exists after rendering
- the library write path already replaces same-id+samename records instead of blindly
  appending

#### Where tension exists

- the current mechanics still permit the prior file to disappear on a same-name export
  because ffmpeg overwrite is the current behavior
- the current library update removes a prior same-id-and-filename record before the new
  one is written, which matches “replace the prior library record for that filename,” but
  that is overwrite semantics, not preservation semantics
- there is no evidence in the inspected slice that the system gates export readiness on a
  combined “file written + hash verified + library written” check as one explicit
  lifecycle contract

#### What is not yet true

- a same-name re-export can still overwrite the prior file
- the system does not appear to keep multiple exports of the same content as separate
  first-class export identities today

### 3. Recording and verifying Library data

#### What the Owner direction implies

- a Library entry can carry a richer set of facts:
  - what the file is
  - export id
  - file type
  - creation time
  - source Content
  - used script version
  - real file location
  - file hash
  - destinations/uses

#### What exists today

- the current library entry already stores a meaningful subset:
  - `id`
  - `filename`
  - `sha256`
  - `exported_at`
  - dimensions and duration
  - `aspect_ratio`
  - `status`
- the project export record already stores more detail than the library entry does

Reference:

- `app/mvp/content.js:1596` to `app/mvp/content.js:1603` for the library entry fields
- `app/mvp/content.js:1592` to `app/mvp/content.js:1655` for the broader export record

#### Where they align

- the current library already has identity, hash, time, file type by extension, and status
- the current system already has the project-level information needed to describe the
  export’s origin

#### Where tension exists

- the current library entry does not, in the inspected shape, store:
  - a separate displayed/human title
  - the destination/use history
  - an explicit “export id” distinct from content id
- the destination/use record is not visible in the inspected export + library flow

#### What is not yet true

- a Library-centered “management center” is not fully present in the inspected slice
- the richer per-export provenance the Owner described is partly present on the project,
  but not fully carried in the Library index in the same form

### 4. Opening a file and sending a file to a destination

#### What the Owner direction implies

- two supported consumption patterns:
  - Path A: send from Library to a destination
  - Path B: open the real file location from Library
- revealing the file location should not encourage direct edits to the stored file

#### What exists today

- the inspected slice clearly has:
  - file writing
  - file probing
  - file hashing
  - library reading and writing
- the inspected slice does not clearly include:
  - a destination-send pathway with authorization and result recording
  - a file-reveal pathway for the user

This is the largest concrete gap in the inspected slice.

#### Where they align

- the system already knows where files live, and already stores the path
- that is the prerequisite for Path B

#### Where tension exists

- Path A is not evidenced in the inspected slice
- Path B is architecturally plausible from current data, but there is no evidence of a UI
  or API endpoint for it here
- the caution about not editing stored files directly is a good governance point, but
  there is no evidence of an enforced mechanism for that caution in the inspected slice

#### What is not yet true

- there is no evidenced destination send
- there is no evidenced file reveal path
- there is no evidenced permission/authorization model for either path in the inspected
  slice

### 5. Separating Content identity from Export identity

#### What the Owner direction implies

- Content is the editable source of truth for the work
- Export is a separate thing with its own file and its own identity
- one Content can lead to many Exports
- re-export does not have to overwrite a prior export if exports are distinct

#### What exists today

- a project has:
  - `content_id`
  - `script_version`
  - `script_version_history`
  - `edit_log`
  - `export`
  - `export.file`, `export.filename`, etc.
- export filename formula is based on content_id and script_version
- library stores by content_id plus filename, and replaces same-id-same-filename entries

Reference:

- `app/mvp/content.js:1560` to `app/mvp/content.js:1561`
- `app/mvp/content.js:1582` to `app/mvp/content.js:1591`

#### Where they align

- the system already has the raw idea that one project can be exported and that the
  export result is recorded
- the system already tracks script version history
- the system already stores hash and path per export

#### Where tension exists

- today, the exported file name is derived from content identity plus script version, so
  export identity is not yet fully independent of content identity and script version
- the library index currently keys by `id` and `filename`, where `id` is the content id
  in the inspected export path
- that means multiple exports are not yet modeled as fully independent export records in
  the library shape inspected here

#### What is not yet true

- a distinct export identity separate from content id is not evidenced in the inspected
  export flow
- a many-exports-per-content registry with independent file identity is not evidenced in
  the inspected slice

## Summary map

### What the system already does

- renders a video to disk with ffmpeg
- overwrites same-name output because ffmpeg is invoked with `-y`
- captures hash, size, dimensions, duration, codec/container, script version, asset refs
- stores a library index with id, filename, sha256, timing, aspect ratio, status
- replaces same-id-same-filename library entries on re-export
- keeps script version history and an export record on the project

### What the Owner direction changes the emphasis toward

- user-facing identity separate from internal filename
- Library as a management center
- two consumption paths
- export identity separate from content identity

### What is still missing or only partly present in the inspected slice

- stable, separate export identity
- human-readable displayed export name
- destination send pathway
- file reveal path
- destination/use history on the export or library entry
- explicit combined readiness gate: file written + hash verified + library written
- an enforcement model for “do not edit stored export files directly”

## Risk and uncertainty notes

### Risk 1 — overwrite is still possible today

Even if exports later get stable names, the current render path can overwrite a same-name
file because ffmpeg is invoked with `-y`.

This means the Owner’s caveat is not just philosophical. It is literally true for the
inspected code.

Reference:

- `app/remotion/render.js:318`
- `app/remotion/render.js:402` to `app/remotion/render.js:406`

### Risk 2 — library replacement is keyed by content id + filename today

The current library replacement logic removes the prior entry when both id and filename
match.

That is not the same as “every export gets a stable independent identity.” It is closer
to “the library tracks the current export file for that content id and that filename.”

Reference:

- `app/mvp/content.js:1582` to `app/mvp/content.js:1591`

### Risk 3 — destination and reveal features are not evidenced here

If the direction depends on “send from Library” or “open file location,” those are not
evidenced in the inspected slice.

That is a real gap for the direction, not a judgment that they are impossible.

### Uncertainty 1 — scope of the repo outside the inspected slice

This task inspected only the listed files. Other files may contain relevant behavior
outside that slice. This document does not claim the absence of such behavior beyond the
inspected slice.

### Uncertainty 2 — what “ready for use” should mean

The Owner direction implies a readiness gate. The inspected code already does pieces of
that, but this document does not assert that the current system already implements the
full combined gate the Owner described.

## What would need to be experimented with before this becomes concrete

These are questions for later, not commitments now:

1. How should export identity be generated if not from `content_id + script_version`?
2. If exports get stable identities, should the library key by export identity instead of
   by content id + filename?
3. Should same-content exports share a folder, or should the folder also be owned by the
   export identity?
4. For Path A, what destinations exist, what authorizations are required, and what
   “sent” records should be kept?
5. For Path B, how should the UI expose the file location without encouraging direct
   edits to stored exports?
6. Should readiness require an explicit three-part success check, and should that check be
   visible in the Library entry?
7. Should the Library entry carry a displayed title separate from the exported filename?
8. Should export history be stored as a list under the Content Project, a list under a new
   Export registry, or both, and what exactly should each store?
