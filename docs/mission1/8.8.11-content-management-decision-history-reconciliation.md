# 8.8.11 — Content Management & Decision History Architecture Reconciliation

**Document:** `docs/mission1/8.8.11-content-management-decision-history-reconciliation.md`
**Purpose:** One evidence-grounded reconciliation of (1) Content Library, (2) Content Lineage, and (3) Decision & History (Four-History Working Model), plus their relationship to the existing ACE workflow.
**What this is:** A documentation-only reconciliation.
**What this is not:** Implementation, a schema proposal, a migration, an authorization, a change to existing Edit/Duplicate/Library behavior, or a ratification of the Four-History model.

---

## 1. Executive Summary

The current ACE repository already separates three kinds of responsibility, but it does not yet have one place that says how they fit together.

1. **Content Library** is currently an export index, not a general content catalog. It is written automatically when a finalized content project is exported, and it is read back through a library-ID lookup.
2. **Content Lineage** is mostly inside a single content project object. The project tracks its own editing history (`edit_log`), its own script version history, and its own snapshot of the offer it was built from. The repository does **not** have a general Parent/Child relationship across content items, and it does not have a general mechanism that says "this content item is a version of that content item."
3. **Decision & History** is handled by several separate things: the workflow state file, the run history, the decision log, the evidence log, and the gate/approval model in the documents. The Four-History Working Model is a **conversation-level working vocabulary**, not a ratified file-backed schema. No file implements H-INTENT/H-UND/H-REQ/H-AUTH tagging.

The important practical conclusion is this: the current code preserves a lot of useful history **inside** a content project and **around** sources, but it does **not** yet connect those histories to the decision histories in a way that is explicit in the data. A single exported video can clearly be linked to the offer it was built from and the content project it was rendered from. But whether that same offer or content project also "belongs to" a requirement history, an understanding history, or an authorization history is not something the data model says directly.

That is the real gap this document is describing.

## 2. Current Architecture Map

The following is a simplified map. It is not a substitute for the source code. It is written so a non-specialist can follow where things live and how they relate.

```

          ┌───────────────────────────────┼───────────────────────────────┐

   ┌──────▼───────┐              ┌────────▼────────┐              ┌──────▼───────┐
   │  Input layer │              │ Workflow/record │              │  Content     │
   │              │              │ layer           │              │  production  │
   │ CSV/Excel    │              │                  │              │              │
   │ export or    │              │  workflow-state  │              │  MVP content │

          ▼                      └────────┬─────────┘              └──────┬───────┘
   Source / Product / Offer / Evidence    │                              │
   records in MVP fixture state           │  plan -> candidate ->        │
   (single JSON state file)               │  content project             │
          │                               │                              │
          │                               ▼                              ▼
          │                      ┌────────▼────────┐              ┌────────▼────────┐
          │                      │  Plan / G2       │              │  Export         │
          │                      │  decision gate   │              │  + publish prep │
          │                      │  (if applicable) │              │  + library      │
          │                      └─────────────────┘              └────────┬────────┘
          │                                                                │
          ▼                                                                ▼
   Observation / reporting layer                              Rendered MP4, still,
   (future; partially scaffolded in docs)                     script markdown, asset files
```

Key idea to keep in mind:

- The **left side** is about where source data comes from and how decisions are recorded.
- The **middle** is the workflow and gate layer.
- The **right side** is the content creation and export layer.

These three areas already exist. What is not yet present is one explicit model that says how a content item, its versions, and its exports relate to the plan, the gate, the requirement, the understanding, and the authorization that may surround it.

## 3. Responsibility Matrix

### 3.1 Content Library

**Owns:**

- A lookup index of exported content items.
- The recorded metadata for each exported item: its id, filename, bytes, sha256, creation time, and the content project id it came from.
- Integrity verification on retrieval: the library lookup checks whether the referenced file exists and whether its actual bytes match the stored sha256.
- The file path convention for exports: a directory per content id under the exports folder.

**Does not own:**

- The content project state itself. That lives in the MVP fixture state file under `contents`.
- Editing, review, QA, finalization, or rendering. Those are handled by the content slice and the renderer.
- General content catalog semantics such as tags, collections, approvals, or ownership. The current library is an export index, not a content management catalog.
- Lineage across content items. It records one exported item's sha256 and content id, but it does not create a general parent/child or version-of relationship between items.

**Evidence:**

- `app/mvp/content.js`:
  - `contentLibraryFile()` resolves the library index path.
  - `readContentLibrary()` reads the index.
  - `getLibraryItem(id)` looks up a single library item by id.
  - `exportProject()` writes the library entry during export.
- `app/mvp/service.js`:
  - `handleContentLibraryItem()` returns the library record plus live file integrity evidence.
- File on disk: `data/mission1/content-library.json` currently contains `[]`.

### 3.2 Content Lineage (what exists now)

**Owns today:**

- A content project's own internal history:
  - `edit_log`: a list of edit events with timestamp, track, scene id, and change description.
  - `script_version` and `script_version_history`: the current script version plus a history of script versions with timestamp, reason, and checksum.
  - `offer_snapshot`: a frozen snapshot of the offer data used when the project was created.
  - `provenance`: a recorded method/provenance note saying the content was created from the export via a deterministic template path.
- A content project's identity:
  - `content_id`, `product_id`, `candidate_id`, `offer_id`, `shop_id`, `plan_id`, `plan_record_id`.
- An export's own identity and integrity:
  - The exported file path, bytes, sha256.
  - The script artifact file, its sha256, and its artifact id.
  - The content library entry for the export.

**Does not own today:**

- A general Parent/Child relationship between content items.
- A general "this content is a duplicate of that content" identity.
- A general "this content is a new version of that content" record type.
- A mechanism that distinguishes "edit the existing project" from "create a new lineage item" in a way that the model declares once and the whole system honors.
- Any concept of Library Edit and how it differs from content-project edit.

**Evidence:**

- `app/mvp/content.js`:
  - `createContentProject()` creates one content project with its internal history fields.
  - `applyVisualEdit()`, `applyTextEdit()`, `applyAudioEdit()`, `addScene()`, `removeScene()`, `reorderScenes()`, `renumberScenes()` mutate a project and push to `edit_log`; duration/audio/text changes can bump `script_version`.
  - `bumpScript()` increases the script version and records a history entry.
  - `finalizeProject()` transitions to FINALIZED and records finalize data.
  - `exportProject()` renders the MP4, creates a still, and writes the library entry.
  - `buildPublishPrep()` transitions to READY_TO_PUBLISH and produces the handoff payload.
- `app/remotion/render.js`:
  - Renders the storyboard to an MP4 using local ffmpeg; produces the actual file bytes and sha256.
- `app/mvp/service.js`:
  - `handleContentDraft()` creates a content project from a candidate/plan.
  - `handleContentTrack()` and `handleContentScenes()` dispatch edits.
  - `handleContentFinalize()` finalizes.
  - `handleContentExport()` triggers export and persists state.
  - `handleContentExportFileByArtifactId()` serves the generated script artifact by artifact id.
  - `handleContentPublishPrep()` builds the ready-to-publish payload.

### 3.3 Decision & History (Four-History Working Model)

**Owns today (concrete records):**

- Workflow state:
  - `data/mission1/workflow-state.yaml` records `current_cycle`, `current_stage`, `stage_status`, `pending_action`, `last_updated`.
- Run history:
  - `data/mission1/run-history.yaml` is an append-only log of actions with timestamp, actor, action text, and result.
- Decision log:
  - `data/mission1/decision-log.md` is the actual decision log in the data tree; at the time inspected it contained DEC-1-G1.
- Evidence log:
  - `data/mission1/evidence-log.md` records sources and findings.
- Gate/approval model and decision-record schema:
  - `docs/mission1/D-data-model.md` §3.8 defines the decision record fields: `id`, `gate`, `decided_at`, `result`, `rationale`, `related_ids`, `approver`.
  - The gate model and approval semantics live in the documents, especially A, B, D, G.

**Does not own today (as a ratified file-backed model):**

- An explicit four-history record type.
- H-INTENT, H-UND, H-REQ, H-AUTH fields or tags in any repository file.
- A defined way to tag one source or event as contributing to more than one history.
- A defined way to record "this source contributed to understanding, and also to requirement discussion, but those are not the same thing" as data rather than as wording.
- A standardized external-source provenance vocabulary or a standardized "authorization claim recorded — source verification open" status field.

**Where the concepts appear anyway:**

- Owner intent-like content appears in strategy/roadmap and G1 direction statements.
- Understanding content appears as drafts and proposals with explicit non-authoritative labels.
- Requirement-like content appears in spec, gate, and experiment-blueprint language.
- Authorization content appears in decision records and gate approval language.
- The separation is real in practice, but it is expressed through document structure and status labels, not through an explicit history taxonomy.

**Evidence:**

- `docs/mission1/D-data-model.md`:
  - §3.8: decision-record schema.
  - §3.3: Experiment record with `success_criteria` sourced or labeled ASSUMPTION.
  - §3.10: WorkflowState fields.
  - §3.11: RunHistory fields.
- `docs/mission1/G-open-questions-decision-log.md`:
  - G1 records with labeled parts for rationale, direction, approval status, approval conditions, and approval limits.
  - Explicit anti-merge language: approval changes only the items below and does not alter other rule sets.
  - Formula approval does not start Experiment 1.
- `docs/mission1/8.8.5-four-history-model-reconciliation.md`:
  - States there is no four-history model file in `docs/mission1/`.
  - States the model is conversation-level.
  - States B5 multi-contribution is practiced through labeled fields, not through a tagging mechanism.
- `docs/mission1/8.8.7-four-history-working-model-alignment-review.md`:
  - Lists the four-history vocabulary and the B1–B11 boundaries.
- `docs/mission1/8.8.9-owner-review-decision-packet.md` and `docs/mission1/8.8.10-r01-multi-history-case-impact-analysis.md`:
  - Confirm the same conclusion from the R-01 angle.

### 3.4 Cross-Component Relationship

At present, the connection between content and decisions is mostly through identifiers and documents, not through a single unified lineage model.

Examples of what is already linkable:

- An exported content item can be tied to:
  - the content project it came from,
  - the offer snapshot inside that content project,
  - the candidate/offer/product/source that fed the content project,
  - the plan that pointed at the candidate,
  - the script version that was exported.
- A source can be tied to:
  - the products, offers, and evidence built from it,
  - the candidates that reference it,
  - the archive status that blocks new generation from it.

Examples of what is less explicit:

- Whether the same offer is "part of" the requirement understanding, the owner's intent, or the authorized scope is not recorded as a first-class relationship. It may be inferable from surrounding documents, but it is not a declared field or link type.
- Whether a correction to team understanding should also change owner intent, requirement, or authorization is not enforced by any lineage rule in the data.

## 4. Existing Behavior

This section reports verified implementation behavior, not intended future behavior.

### 4.1 Identity and storage

- Content items are identified by `content_id`, allocated as `CNT-N` from the current number of contents in the state.
- The main content state is stored in one JSON file:
  - default `data/mvp/fixture-state.json`,
  - overridable by `ACE_MVP_STATE_FILE`.
- The state file is written through a temporary-file-then-rename pattern, so a write is not a live in-place edit of the final file. This is a recovery-friendly write convention, but it is not a version history of content.
- The content library index is a separate file:
  - default `data/mission1/content-library.json`,
  - overridable by `ACE_CONTENT_LIBRARY_FILE`.
- The library index currently contains an empty array. It is populated by export, not by content creation.

### 4.2 Creation

- Content is created from a saved or queued candidate, optionally via a plan.
- Creation produces one content project with:
  - a fresh content id,
  - the selected approach,
  - the storyboard,
  - the script,
  - the offer snapshot,
  - provenance,
  - source and evidence ids,
  - an empty edit log,
  - a script version history entry for version 1.
- The content project is persisted in the state file's `contents` map and added to `contentOrder`.

### 4.3 Editing

- Edits mutate the same project object in place.
- Each edit:
  - changes the scene or project fields,
  - may update audio status,
  - bumps `storyboard.version` or `script_version` when relevant,
  - sets `updated_at`,
  - appends an entry to `edit_log`.
- Script changes also record a `script_version_history` entry with version, time, reason, and checksum.
- There is no "new version of the content item" object created by editing. The same content id continues to represent the current edited project.

### 4.4 Duplication

- There is no content duplication endpoint or function in the inspected slice.
- There is duplication-like behavior for **candidates** under a replace/add pattern, but that is part of the candidate workflow, not content lineage.
- For content, the only way to start a comparable new item is to create a new content project from scratch, which loses the direct "this is a copy of that content" identity unless an agent or workflow adds it separately.

### 4.5 Export

- Export only runs from a FINALIZED project.
- Export:
  - renders the MP4 with local ffmpeg,
  - produces a still frame,
  - records the exported file path, bytes, and sha256,
  - writes an entry into the content library index that includes the library id, filename, bytes, sha256, created_at, content_project_id, and content_id.
- The rendered file lives under `exports/<content_id>/`, with the filename `<content_id>-v<script_version>.mp4`.
- A script markdown artifact can also be generated and persisted on the project under `artifact`, with its own artifact id and sha256. That artifact can be served through a separate artifact-id endpoint.

### 4.6 Publish preparation

- Publish preparation requires an EXPORTED project.
- It transitions the project to READY_TO_PUBLISH, records a prepare timestamp and edit-log entry, and returns a handoff payload.
- The slice explicitly does not publish to any external platform.

### 4.7 Recovery and integrity

- Recovery-oriented mechanisms that exist:
  - state writes use temp-rename,
  - export uses a per-content-id output directory,
  - the library lookup verifies file existence and sha256 match on retrieval,
  - asset files referenced by a project must exist in the project's assets for a finalize/edit to treat them as bound,
  - the source archive log preserves why a source was archived and what evidence/candidates existed at archive time.
- Recovery-oriented mechanisms that do not exist today:
  - There is no git-based content version history inside the content slice itself. Git is available in the repository, but the content slice does not create git commits for content edits.
  - There is no content backup/archive separate from the current state file.
  - If the state file is lost or corrupted, the content history inside it is not independently preserved by the slice.
  - If an exported file is deleted from disk, the library record still exists, but retrieval will report the file as MISSING.

### 4.8 Orphan and replacement behavior

- If a content project is edited, the earlier in-memory states are not preserved as separate objects by the slice. Only the `edit_log` and `script_version_history` remain as recorded history inside the same project.
- If an export is later re-exported after another edit, the new export is a new file with a new sha256. The library currently writes one entry per export action; the inspected code does not, by itself, preserve a full chain of exported versions under a single declared lineage id.
- If the library index is lost, exports can still exist on disk, but the library lookup will not find them.

## 5. Scenario Walkthroughs

Each walkthrough states what happens, which component is responsible, what should be preserved, which histories may be relevant, and what must not be inferred automatically.

### Scenario 1 — Edit an existing content item

**What happens:**

- A track edit is applied to a scene: visual, text, or audio.
- The project's `storyboard.version` or `script_version` may increase.
- `updated_at` changes.
- A new entry is appended to `edit_log`.
- If the edit changes script text, a new `script_version_history` entry is recorded.
- The project remains the same content id.

**Component responsible:**

- Content slice for edit semantics.
- Service layer for the endpoint dispatch and state persistence.
- Renderer is not involved unless an export is requested later.

**What should be preserved:**

- The edit event in `edit_log`.
- The script version history if the script changed.
- The offer snapshot, so later readers can tell what offer the content was built from.
- The identities: content, product, candidate, shop, plan.
- Any evidence ids attached to the scenes.

**Histories that may be relevant:**

- H-UND if the edit reflects a team/agent interpretation change.
- H-REQ if the edit was made to meet a requirement or acceptance condition.
- H-INTENT if the edit reflects a changed direction.
- H-AUTH if the edit was made under an explicit authorization or gate outcome.

**What must not be inferred automatically:**

- An edit does not automatically mean owner intent changed.
- An edit does not automatically mean requirement changed.
- An edit does not automatically mean authorization changed.
- A later edit does not make the earlier `edit_log` entries false; it only means the project moved on.

### Scenario 2 — Duplicate an existing content item

**What happens today:**

- There is no dedicated content duplication operation in the inspected slice.
- Starting a similar item means creating a new content project, which will get a new content id and a new edit log.
- Any "duplication" relationship would have to be recorded outside the slice, for example in the state file, the documents, or a future lineage field.

**Component responsible today:**

- None for content duplication specifically.
- Content creation is responsible for making a new project, but it does not declare the new project as a duplicate of another.

**What should be preserved if duplication were added:**

- A clear statement whether the new item is independent or derived.
- The source content id, if it is derived.
- The point in time and the reason for duplication.
- The distinction between "same content, new copy" and "same topic, new independent content."

**Histories that may be relevant:**

- H-UND if the duplication reflects an interpretation or drafting choice.
- H-REQ if the duplication was required to fulfill a format or channel need.
- H-AUTH if the duplication was explicitly authorized.

**What must not be inferred automatically:**

- A duplicate does not inherit the authorization of the original by default.
- A duplicate does not inherit the requirement or understanding status of the original by default.
- A duplicate is not automatically the same decision object as the original.

### Scenario 3 — Edit or replace an item through Content Library

**What happens today:**

- The Content Library is not an edit surface for content projects.
- The library is written by export.
- The library can be read by id and can verify file integrity.
- If you mean "edit the exported item," the real edit path is to edit the content project and re-export.

**Component responsible:**

- Content slice for the project.
- Renderer for the export.
- Content library for recording the resulting export metadata.

**What should be preserved:**

- The old export file and its sha256 if it still matters.
- The new export file and its sha256.
- The content id lineage inside the project.
- The fact that the library represents an export index, not the source of truth for the project itself.

**Histories that may be relevant:**

- H-UND for the reason the re-export happened.
- H-REQ if the re-export was done to meet an acceptance condition.
- H-AUTH if the re-export was authorized or gated.

**What must not be inferred automatically:**

- A new export does not erase the old export's existence unless the old file is actually removed.
- A library entry is not the same thing as the content project.
- Replacing an export file does not by itself change intent, requirement, or authorization.

### Scenario 4 — Change an Owner intention without editing content

**What happens:**

- Nothing in the content slice changes by itself.
- The relevant change would be recorded in the decision log, the workflow state, the roadmap, or another decision record, depending on what changed.

**Component responsible:**

- Decision/gate layer for recording the Owner's changed intention.
- Content slice only if content is later edited to reflect the new intention.

**What should be preserved:**

- The original intention as it was recorded.
- The new intention as a separate record or amendment.
- The time of the change.
- The scope of what the changed intention affects.
- The fact that content, if unchanged, still reflects the prior state.

**Histories that may be relevant:**

- H-INTENT is the primary history here.
- H-AUTH if the change also changes authorization.
- H-REQ if the change also changes a requirement.
- H-UND if the team needs to reinterpret prior content in light of the new intention.

**What must not be inferred automatically:**

- A change in recorded intention does not automatically change existing content.
- A change in intention does not automatically become a requirement.
- A change in intention does not automatically become authorization.
- Content that was created under a prior intention is not automatically "wrong"; it may just be out of date with respect to intent.

### Scenario 5 — Correct a team's misunderstanding without changing the Owner's original intent

**What happens:**

- The correction is recorded as understanding.
- The Owner's intent record stays as it was.
- If content was based on the misunderstanding, the content may later be edited, but that is a separate action.

**Component responsible:**

- Decision/understanding records for the correction.
- Content slice only if content changes.

**What should be preserved:**

- The original misunderstanding, if it was recorded, so the correction has a target.
- The correction and who made it and when.
- The Owner's original intent record unchanged.
- Any content that was affected, marked as needing review or update if applicable.

**Histories that may be relevant:**

- H-UND is the primary history.
- H-INTENT stays separate, because the Owner's intent did not change.
- H-REQ only if the misunderstanding was also reflected in requirement wording.
- H-AUTH only if the misunderstanding had been mistaken for authorization.

**What must not be inferred automatically:**

- Correcting understanding does not mean the Owner changed intent.
- Correcting understanding does not automatically authorize a content change.
- A correction is not the same as a rejection of prior work unless that is explicitly decided.

### Scenario 6 — Change a Requirement or authorization through an explicit Owner decision

**What happens:**

- An explicit decision record or gate outcome records the change.
- The content slice does not auto-update content to match.
- Any affected content or plan must be reconciled separately.

**Component responsible:**

- Decision log or gate record for the authorization/requirement change.
- Content or plan layers only when someone acts on the change.

**What should be preserved:**

- The prior requirement or authorization state.
- The new decision record.
- The scope and limits of the new authorization.
- The relationship to affected content, plans, candidates, or experiments if any.
- The fact that implementation may lag behind authorization.

**Histories that may be relevant:**

- H-REQ for the requirement change.
- H-AUTH for the authorization change.
- H-INTENT if the change also reflects a shifted direction.
- H-UND if the team must reinterpret earlier content or plans.

**What must not be inferred automatically:**

- A requirement change is not automatically an authorization.
- An authorization change is not automatically a content change.
- An authorization change does not retroactively rewrite the history that led to the prior state.
- Approval of a change does not mean the prior version was unauthorized; it means the new state is now authorized.

## 6. Gaps & Risks

These are actual gaps and risks from the inspected evidence. They are not speculative requirements.

### G1 — No general content lineage model

**Observation:**

The content slice gives each project its own internal history, but it does not define a general lineage relationship between content items.

**Evidence:**

- `app/mvp/content.js` has `edit_log`, `script_version`, `script_version_history`, `createContentProject()`, and the edit functions, but no parent/child or version-of structure between content ids.
- `app/mvp/service.js` has creation, editing, finalization, and export endpoints, but no content duplication or version-linking endpoint.
- `data/mission1/content-library.json` is an export index; it does not define a content catalog or lineage graph.

**Risk:**

- It is hard to answer "is this content the same item as that content, or a new item, or a version of that item?" using only the current data.

### G2 — No "Library Edit" concept distinct from project edit

**Observation:**

The library is written by export and read by id. There is no separate library editing story.

**Evidence:**

- `app/mvp/content.js` `exportProject()` writes the library entry.
- `app/mvp/service.js` `handleContentLibraryItem()` reads it back with integrity checks.
- There is no library update or edit path beyond re-export.

**Risk:**

- If a library record is wrong, the fix path is not obviously "edit the library"; it is likely "fix the content project and re-export," but that is not yet a declared rule in the data.

### G3 — Exports are recorded, but an exported-version chain is not a declared lineage

**Observation:**

Each export writes its own file and library entry, but the current code does not formally link "export v1, export v2, export v3" as a declared sequence under one content lineage concept.

**Evidence:**

- `exportProject()` writes `<content_id>-v<script_version>.mp4` and a library entry with `content_project_id` and `content_id`.
- There is no separate exported-version object type in the inspected code.

**Risk:**

- You can reconstruct some of the chain from file names and script versions, but the model does not declare the chain as a first-class lineage.

### G4 — Recovery is partial

**Observation:**

Some recovery aids exist, but content history is not independently preserved outside the state file.

**Evidence:**

- State writes use temp-rename.
- The library verifies sha256 on read.
- Source archive log preserves archive-time evidence/candidate links.
- No content backup, no per-edit git snapshot, and no separate content archive are implemented in the inspected slice.

**Risk:**

- If the state file or export directory is lost, the content history and exports can be lost together.

### G5 — The Four-History model is not a ratified data model

**Observation:**

The four-history concepts exist in documents and task reports, but no file implements them as fields or tags.

**Evidence:**

- `docs/mission1/8.8.5-four-history-model-reconciliation.md` says there is no four-history model file in `docs/mission1/` and that the model is conversation-level.
- `docs/mission1/D-data-model.md` §3.8 defines the decision record, not four-history records.
- `docs/mission1/G-open-questions-decision-log.md` already separates things by labeled fields, which is why the concepts are partially reflected in practice.

**Risk:**

- People can talk past each other by assuming the working vocabulary is already a data model.
- Multi-history contribution is currently implicit, not declared.

### G6 — The link between content and decision histories is mostly documentary

**Observation:**

Content can be tied to a plan, candidate, offer, and source through identifiers. But whether that content also relates to intent, requirement, understanding, or authorization is not encoded as a declared relationship.

**Evidence:**

- Content carries `plan_id`, `candidate_id`, `offer_id`, `product_id`, `shop_id`, `source_ids`, `evidence_ids`.
- Content does not carry a declared history tag set, approval class, or requirement relationship type.
- `docs/mission1/G-open-questions-decision-log.md` keeps approval and rationale separated by labeled parts, which is good practice, but it is document structure, not a content field.

**Risk:**

- The same exported content can be referenced in several histories, but the repository does not make that multi-history relationship explicit or guard against merging the meanings.

### G7 — Provenance is strong for content origin, but not yet for decision provenance classification

**Observation:**

Content provenance is explicit: method, source, limitations, offer snapshot, evidence ids. Decision provenance is present in decision records and run history, but there is no standardized field classifying a decision-like statement as intent, understanding, requirement, or authorization.

**Evidence:**

- `createContentProject()` records detailed provenance and limitations.
- `docs/mission1/D-data-model.md` §3.8 records `approver: "owner"`, but does not define a history-class field.
- `docs/mission1/8.8.5-four-history-model-reconciliation.md` explicitly lists this as a proposed addition, not a current field.

**Risk:**

- A decision-like statement can be ambiguous about whether it is intent, understanding, requirement, or authorization unless the reader also knows the document context.

---

## 7. Proposed Responsibility Boundaries

These are recommendations. They are proposals, not accepted requirements and not authorized changes.

### P1 — Content Library should own the export index and integrity lookup, not the content project

- Keep the library as the export index and integrity gateway.
- Do not turn it into the primary content state store.
- If the library is ever expanded, expand it as a catalog on top of the existing content state, not as a replacement for it.

### P2 — Content project should own the working copy and its internal history

- Keep `edit_log`, `script_version_history`, `offer_snapshot`, provenance, and identities on the project.
- Treat the project as the live editable object.
- If a new version or copy is needed, decide explicitly whether to mutate the existing project or create a new one, and record that decision.

### P3 — Lineage should be a declared relationship, not an accidental file naming pattern

- If the project wants parent/child, duplicate, or version-of semantics, those should be explicit fields or link records, not inferred from file names or script versions alone.
- If a content item is a duplicate or derived copy, the source id and the derivation reason should be recorded.
- If a content item is a new version of an earlier item, the earlier item and the reason for supersession should be recorded.

### P4 — Exports should be traceable as artifacts of a content project, with their own integrity record

- Keep the export file, sha256, still, and library entry.
- If the project wants an exported-version chain, add it as a declared list or link set attached to the content project or the library, not as an implicit naming convention only.

### P5 — Decision and history should keep their current separation, and the four-history vocabulary should stay a vocabulary until the Owner decides otherwise

- Keep workflow state, run history, decision log, evidence log, and gate model as they are.
- Keep the existing strong separation language already present in the documents.
- Do not turn H-INTENT/H-UND/H-REQ/H-AUTH into a schema change unless that is an explicitly authorized decision.
- If the model wants B5 to be provable in data, it should propose an explicit mechanism rather than assume current document structure already satisfies it.

### P6 — Multi-history contribution should be representable without merging meanings

- If one source, offer, or content item touches more than one history, the system should be able to say so while keeping each history's meaning, status, and provenance distinct.
- This is the central architectural recommendation coming out of this reconciliation and from the R-01 analysis.

## 8. Unresolved Owner Decisions

These are the decisions that genuinely require Owner authority. The team may recommend, but may not decide.

1. **Whether content lineage should become an explicit data relationship.** Current behavior gives each project its own history and exports a library entry, but there is no declared parent/child/duplicate/version relationship. Whether that matters enough to build is an Owner decision.

2. **Whether the Content Library should remain an export index or become a broader content catalog.** Current behavior is export-index only. Broader catalog semantics would be a new responsibility.

3. **Whether "edit" and "new version/copy" should be different operations with different lineage consequences.** Current behavior mutates the same content id. A different model would require a deliberate choice.

4. **Whether the Four-History Working Model should become a ratified data model, stay a working vocabulary, or be retired/replaced.** No file currently implements it. That is a content/decision-model decision, not a content-slice implementation detail.

5. **Whether multi-history contribution should be made provable in data, and if so, by what mechanism.** The existing documents already separate meanings in practice, but they do not declare the relationship in a way the data model exposes.

6. **Whether recovery/integrity protection for content should be strengthened beyond the current temp-rename write, sha256 library check, and source archive log.** Any such change is an implementation decision with storage and operational implications.

7. **Authorization provenance for decision-like records outside the canonical decision log.** This is an open U-1 matter. It is mentioned here because it affects how confidently the decision/history layer can be trusted, but this task does not resolve it.

---

## 9. Recommended Next Steps

These are ordered by what should be clarified before more is built.

1. **Confirm the intended content model scope.** Decide whether the Content Library is only an export index or should become a fuller content catalog, and whether content items can be duplicated or versioned as first-class objects.

2. **Decide whether content edits are in-place mutations or versioned objects.** That choice drives everything else in lineage: identifiers, history, exports, and recovery.

3. **If lineage is wanted, define the minimum link types first.** A small set is enough to start: source-of-truth content id, derived-from content id, duplicate-of content id, superseded-by content id, exported-artifact link.

4. **Keep decision history and content history separate by design, with explicit cross-references where needed.** Do not merge the two by assuming shared identifiers mean shared meaning.

5. **Preserve the strong existing separation language in the documents.** The documents already do a lot of the separation work that a future model would want to formalize. That is an asset, not something to lose.

6. **If the Four-History model is to be made more concrete, do it as a separate decision with its own review, not as a side effect of content work.** This task found that the working vocabulary and the content/data model are currently different layers. Mixing them prematurely would likely create more confusion than clarity.

The sequence is ordered this way because content lineage and decision history touch the same objects from different directions. If the Owner decides the content model first, the four-history question becomes easier to place. If the four-history question is decided first, content lineage can be designed to respect it. Either order is acceptable, but the two should not be solved by accident at the same time.
