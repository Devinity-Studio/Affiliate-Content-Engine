## 3. Redacted Evidence Bundle — incorporated recommendation

The recommended evidence format for the first successful slice is a Redacted Evidence Bundle connected by one trace ID across four stages:

1. ACE Runtime Request
2. OpenRouter Provider Response
3. ACE Validation and Normalization
4. Final ACE Script Draft Result

### Recommended evidence artifacts

- `trace-record.json` — primary structured record containing:
  - trace ID
  - timestamp
  - operation
  - provider
  - model
  - source
  - status
  - latency
  - token usage, when available
- `script-draft.txt` — the actual script draft returned and accepted by ACE.
- `runtime-log.txt` — concise runtime events correlated by the same trace ID.

### Trace relationship

- A single trace ID generated by ACE Runtime should tie the request, the provider response, the normalization outcome, and the final accepted script draft together.
- The trace ID should be generated in ACE Runtime, not derived from the provider, so the bundle can demonstrate origination from ACE.
- The same trace ID should appear in the runtime log entries that surround the request, the response handling, and the accepted output.

**PROPOSED**

---

## 4. Evidence integrity requirements

The evidence must satisfy these integrity constraints:

- The request must be shown to originate from ACE Runtime, not from a separate manual API test.
- Provider and model information must correspond to the actual response for that trace.
- The final Script Draft must be the content ACE actually received and accepted after validation.
- `source` must distinguish `LIVE_LLM`, `TEMPLATE`, and `MOCK`.
- `status` must be recorded independently from `source`.
- If the provider call fails and ACE falls back to deterministic output, the final result must be labeled `TEMPLATE` with an appropriate fallback status. It must never be presented as `LIVE_LLM`.
- Evidence must not be fabricated, reconstructed, or manually substituted for a real provider exchange.

**PROPOSED**

---

## 5. Secret and privacy boundaries

The first evidence bundle should contain only the minimum information required to verify the integration.

### Never store or expose

- API keys or Authorization headers
- Environment secrets
- Unredacted credentials
- Sensitive raw provider payloads without explicit approval

### Retention defaults pending Owner approval

- Prompt retention, raw response retention, and any external telemetry transmission require separate approval if they contain sensitive data.
- PostHog remains disabled by default.
- The exact storage location and retention policy for the evidence bundle are still unresolved.
