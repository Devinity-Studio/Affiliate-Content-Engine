## C. Four-History Interaction

The working model's central idea — one source/event may contribute to multiple histories with each contribution keeping its own meaning and provenance — is **conceptually sound and partially reflected in the repository's document structure**, but it is not yet expressed through any history-tagging mechanism.

**Grounded example 1 — Record G1-A in `docs/mission1/G-open-questions-decision-log.md`:**

- L38–L40: states G1 direction and pre-G1 policy — this content functions as H-INTENT (direction) and also as H-AUTH (approved scope/policy).
- L37: "Status: APPROVED." — this is H-AUTH (authorization result).
- L42: rationale referencing Docs A/B/E/F — this is reasoning that belongs to H-INTENT/H-UND, kept distinct from the approval result.
- The same record contributes to H-INTENT and H-AUTH, but the record uses `Status`, `Content`, and `Rationale` to separate the authorization result from the direction/reasoning.
- **What this shows:** one record contributes to multiple histories without merging the meanings, because the record structure separates aspects. This is exactly what B5 says should happen.
- **Limitation:** no file labels these contributions as H-INTENT or H-AUTH; the separation is achieved by field labels, not by a history taxonomy.

**Grounded example 2 — Record G1-E in `docs/mission1/G-open-questions-decision-log.md`:**

- L72–L81: "Continuous optimization & sustainable-income principle" — proposed as an operating principle (H-INTENT/H-UND direction), approved as an operating principle (H-AUTH, but with explicit limits: "documentation alignment authorized; no change to gates, budget, or accounting rules").
- L73 and L79–L80: the approval is bounded — this is H-AUTH with explicit limits, not a blanket authorization.
- **What this shows:** an intent-like principle can be approved in a bounded way without becoming a requirement or a gate authorization. That is a live demonstration of the intent→authorization boundary in practice.
- **Limitation:** again, no file labels these as H-INTENT/H-UND/H-REQ/H-AUTH.

**What cannot be grounded yet:**

- No file in the repository demonstrates a **H-REQ** record with an explicit approval-status field that is separate from the H-AUTH record. The closest is the Experiment record (`docs/mission1/D-data-model.md` §3.3) which has `success_criteria` sourced or labeled ASSUMPTION — a requirement-ish statement that is not an authorization. But no file explicitly models "requirement record with approval status" as a separate history-tracked object; the approval-status concept appears in the decision record (`approver: "owner"`) and in gate descriptions.
