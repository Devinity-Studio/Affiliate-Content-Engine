## R-01 — Explicit multi-history mechanism

**Related boundary:** B5 (one source may contribute to more than one history).

### 1. Original proposal

The working model should provide an explicit way to say that one source, event, or piece of evidence genuinely contributes to more than one history without merging the meanings of those histories or transferring authority between them. In Task 8.8.8 this is labeled F-01.

### 2. Plain-language explanation

Right now, the project's documents already separate things by labels, by status, and by which file they live in. That separation is useful. The proposal asks for something stronger: an explicit model convention for expressing that a single thing can feed multiple histories at the same time, with each history keeping its own meaning.

In other words, the problem is not that the documents are disorganized. The problem is that "the documents happen to be separated" is not the same thing as "the model can explicitly say a source contributes to several histories."

### 3. Concrete example

A better, non-historical example: imagine a single public research page about a Thailand affiliate program. The same page could matter to several different lines of thinking at once:
- whether the program's terms look plausible for planning,
- whether a particular claim made in a draft script is supported,
- whether a measurement assumption is reasonable before the experiment starts.

Today, those concerns could be recorded in different places with different labels. What the proposal is asking about is whether the model should also be able to say, in a deliberate way, "this one source contributed to all three lines of thinking, but it did not make them the same thing and did not transfer approval between them."

This example is illustrative of the kind of issue the proposal addresses. It is not presented as an actual historical finding.

### 4. Proposed treatment

If adopted, B5 would stop being only a pattern you can notice in the documents and become something the working model can express directly. That could mean an explicit tagging convention, a metadata rule, or some other documented way of saying that a contribution is shared across histories without collapsing them.

What it would mean even more concretely: a future writer would not have to rely on "they are in different files and labeled differently, so they must be different." The model would also have an explicit statement of the multi-history relationship.

### 5. Consequences of adoption

**Possible benefits:**
- The project would have a clearer way to describe a real phenomenon: one source or event can be relevant to several different histories at once.
- It would reduce the chance of later talking as if multi-history contribution is already an operational feature just because the documents are separated by labels and folders.
- It could make future model explanations easier to follow, at least for this specific issue.

**Complexity and operational impact:**
- Some concrete form would need to be specified: what fields, tags, or conventions would actually carry the meaning.
- People would need to learn and consistently use that convention.
- If the convention is too heavy, it could become paperwork rather than a useful distinction.

**Possible risks:**
- If the wording is too concrete, someone may later mistake a proposal for an implemented mechanism.
- If the convention is too vague, it may add wording without adding usable meaning.
- A poorly drafted mechanism could accidentally encourage people to claim a source "contributes" to a history in a way that is not actually supported by evidence.

### 6. Consequences of rejection or deferral

**If rejected:** the documents keep their current separation by labels and status, but the project does not adopt an explicit multi-history-contribution convention. The practical gap is that future writing may still blur the difference between "separated by convention" and "explicitly modeled."

**If deferred:** the question is postponed until there is either a real case that motivates it or more clarity about what concreteness is actually wanted. That is reasonable if the issue is not yet pressing.

**What remains unresolved either way:** whether the current separation-by-labels pattern is enough, or whether the project really needs a deliberate model concept for shared contributions across histories.

### 7. Evidence and provenance

**Observed evidence:** The existing documents do separate meaning by labeled fields and by document status; that much is present in the current document set.

**Existing document content:** The underlying separation exists in current planning documents and in the working reconciliation material. No existing file implements H-INTENT/H-UND/H-REQ/H-AUTH tagging or any history-contribution metadata convention.

**Team/agent proposal:** The explicit B5 mechanism itself is an agent/team synthesis. The underlying separation is real; the explicit mechanism is not.

### 8. Unresolved questions

- Do we actually need an explicit model mechanism, or is the current separation by labels and status sufficient for real work?
- If we do want one, how concrete should it be before it becomes a burden?
- Should this be decided on principle now, or only when a real case shows the current separation is not enough?

## R-02 — Fixed provenance-status vocabulary

**Related boundary:** B6 (source status distinctions).

### 1. Original proposal

The working model should adopt a fixed vocabulary for describing the status of an external source or piece of evidence. In Task 8.8.8 this is labeled F-02. The vocabulary would distinguish ideas such as:
- the source exists and is accessible,
- the source exists but is currently inaccessible,
- the source is referenced but not independently verified,
- provenance is unknown,
- no inspectable source was found in the reviewed scope.

### 2. Plain-language explanation

People already talk about sources in similar ways across documents, but not always in the same words. The risk is that different summaries may quietly drift into different meanings: "referenced" may later be read as "checked," or "inaccessible" may later be read as "does not exist."

The proposal is to agree on a small set of source-status labels so that the project says the same thing in the same way every time.

### 3. Concrete example

Imagine a source that the project wants to cite:
- If you can open it today and read what it says, that is one situation.
- If the page or file exists, but you cannot reach it right now, that is a different situation.
- If someone points to it as if it exists, but nobody has confirmed it, that is yet another situation.
- If no inspectable source was found at all in the reviewed scope, that is a fourth situation.

Without a fixed vocabulary, one document might describe the same situation as "unverified," another as "not checked," and another as "unavailable," and later readers may treat those as interchangeable when they are not.

This example illustrates the kind of problem the proposal targets; it is not presented as a specific historical record.

### 4. Proposed treatment

If adopted, the project would stop relying on ad hoc phrasing for source status and would use a fixed set of labels with shared meaning. That does not automatically make any source verified; it just makes the status language more uniform.

### 5. Consequences of adoption

**Possible benefits:**
- More consistent language for accessibility, verifiability, and provenance.
- Lower chance of accidentally treating "referenced but not verified" as "verified."
- Lower chance of treating "inaccessible right now" as "does not exist."

**Complexity and operational impact:**
- The vocabulary would need to be defined precisely enough to be useful.
- Once defined, the project would have to keep using it in summaries, evidence notes, and decision text.
- People would need to decide which label applies in each case, which is not always trivial.

**Possible risks:**
- A vocabulary that is too rigid could be forced onto situations where it does not fit well.
- Uniform wording can create a false sense that the underlying evidence is more structured than it really is.
- If the labels are too many or too subtle, they may be applied inconsistently in practice.

### 6. Consequences of rejection or deferral

**If rejected:** the project continues to use informal source-status language. That can still work, but it depends on careful reading and consistent habits rather than a shared label set.

**If deferred:** the issue is postponed until the project has more experience with how often source-status confusion actually causes trouble.

**What remains unresolved either way:** whether the current informal language is actually causing harmful confusion, or whether the consistency benefit is worth the added discipline.

### 7. Evidence and provenance

**Observed evidence:** Existing docs already express similar ideas in an informal way. For example, working material has used language along the lines of "cited as normalization model only," "no external artifact claimed," and "unverified sources are never implied as checked."

**Existing document content:** The spirit of the vocabulary already appears in the current document set. What is proposed is the fixed, standardized version of that language.

**Team/agent proposal:** The fixed vocabulary itself is an agent/team proposal, informed by the existing informal usage and by the corrected framing in which an inaccessible source was marked UNREVIEWED rather than being silently erased.

### 8. Unresolved questions

- How many status labels are enough, and how fine-grained is too fine?
- Should the vocabulary be enforced strictly, or used as a recommended convention?
- Are there real cases in the current project where inconsistent source-status language has already caused confusion, or is this mainly preventive?

## R-03 — Term-sense / entity-resolution rule

**Related boundary:** B7 (avoiding false equivalence when labels happen to match).

### 1. Original proposal

The working model should adopt a rule, or a disambiguation mechanism, that stops records from being connected merely because their text labels match. In Task 8.8.8 this is labeled F-03. A central illustration is the distinction between `profile_bio` as a link-form term and any other concept that might also be called "Profile."

### 2. Plain-language explanation

Two things can share a similar name without being the same thing. If a project later sees the word "Profile" in different contexts, there is a real risk of assuming those contexts refer to the same concept just because the word looks the same.

The proposal is to make the model have a deliberate rule for when similar words should and should not be treated as the same entity.

### 3. Concrete example

In the current planning documents, `profile_bio` is used as a publishing link-form term. That is one meaning.

Now imagine that, outside the current planning set, the Owner has a concept called something like "Profile" or "Content Library." If later work treats the planning vocab word `profile_bio` and the external Owner concept as if they were the same thing because both contain the word "Profile," that would be a false equivalence.

The risk is not that the current planning documents are internally inconsistent. The risk is that an external concept could be retrojected onto the existing vocabulary and silently merged with it.

This example illustrates the kind of term-sense problem the proposal addresses; it is not presented as an already-confirmed Owner concept.

### 4. Proposed treatment

If adopted, the project would have an explicit rule or mechanism for entity reference or term-sense disambiguation. That could be a convention, a naming rule, or some stronger structure. The point is to keep similar labels from being treated as proof of identity.

### 5. Consequences of adoption

**Possible benefits:**
- Lower risk of merging different concepts because of similar wording.
- A clearer rule for future writers and reviewers.
- Better protection against importing an external concept into the planning vocabulary without evidence.

**Complexity and operational impact:**
- The disambiguation rule would need to be defined clearly.
- If it is too elaborate, it could be harder to follow than the actual risk justifies.
- Someone would have to decide, in each case, whether two uses of a word are the same thing or not.

**Possible risks:**
- The mechanism could be over-engineered if the real risk is narrower than the mechanism implies.
- If defined too loosely, it may not actually prevent the confusion it is meant to prevent.
- If defined too rigidly, it may create artificial separations where the meanings really are the same.

### 6. Consequences of rejection or deferral

**If rejected:** the project continues to rely on term-sense discipline by convention. That is currently the state of the planning set.

**If deferred:** the issue is postponed until the term collision risk becomes more concrete.

**What remains unresolved either way:** whether convention and careful reading are enough, or whether the project needs a stronger rule because the risk is persistent or high-impact.

### 7. Evidence and provenance

**Observed evidence:** The current planning set already preserves term-sense discipline for `profile_bio` in the link-form sense. The term "Content Library" does not currently appear in the Mission 1 planning docs.

**Existing document content:** The internal consistency of the planning vocabulary is a real, current feature. What is not verifiable from repo evidence is any external Owner concept that might later be called "Profile" or "Content Library."

**Team/agent proposal:** The proposed disambiguation approach is an agent/team synthesis, grounded in a real term-collision risk but not yet tied to a demonstrated merged record in the current set.

### 8. Unresolved questions

- Is the main risk external retrojection of an Owner concept, or is there also an internal risk within the current document set?
- Should disambiguation be a naming convention, a metadata rule, or something else?
- Do we need this rule now, or only if and when an external Owner concept starts appearing in project work?

## R-04 — Explicit authorization-claim status label

**Related boundary:** B8 (distinguishing claims of Owner approval from verified Owner authorization).

### 1. Original proposal

When an agent-authored document records a claim that the Owner approved something, the document should preserve that claim as a claim when the original Owner source is unavailable or unverified, instead of silently promoting it to verified authorization or silently discarding it. A possible convention is a status such as "Authorization claim recorded — source verification open." In Task 8.8.8 this is labeled F-04.

### 2. Plain-language explanation

Sometimes a document says "the Owner approved X." That statement may be accurate, or it may be a record of someone's understanding of an approval. If the actual Owner source that would confirm it is not available or not verified, the document should still be honest about what kind of record it is.

The proposal is to give that situation an explicit status label, so that a claim is not accidentally upgraded to verified authorization just because it has been written down.

### 3. Concrete example

Suppose a working note says, "G1 direction was approved by the Owner." That may be true. But if nobody can currently point to the specific Owner source that verifies that claim, then the note is still a claim, not necessarily a verified authorization record.

Without an explicit status label, later summaries may blur that distinction. They may write as if the approval has been independently verified, or they may quietly drop it because the source is not handy. Either outcome would be worse than saying plainly: this is a claim; its verification is open.

This example illustrates the claimed issue; it is not presented as proof that any particular existing record is wrong.

### 4. Proposed treatment

If adopted, the project would use a standard phrase or status for authorization claims whose source verification is still open. That would make it easier to tell claims apart from verified authorization in records and summaries.

### 5. Consequences of adoption

**Possible benefits:**
- Clearer separation between claims and verified authorization.
- Easier to track which approval statements still need source verification.
- Less chance of later summaries treating a claim as if it had already been confirmed.

**Complexity and operational impact:**
- The exact status wording and the actions that follow from it would need to be defined.
- The project would have to apply the label consistently where relevant.
- It may raise follow-up questions about who is responsible for closing the verification.

**Possible risks:**
- If the wording is too formal, a claim may look more authoritative than it is.
- If the label is applied carelessly, it could be interpreted as a verdict on the claim itself rather than on the state of its verification.
- There is a danger of making the process look resolved when it is not.

### 6. Consequences of rejection or deferral

**If rejected:** the project continues to separate claims from verified authorization in principle, especially through careful wording, but without a standard claim-status label.

**If deferred:** the issue is postponed until the project sees whether the lack of a standard label actually causes problems in practice.

**What remains unresolved either way:** whether the current informal separation is sufficient, or whether the absence of a standard label is creating real confusion.

### 7. Evidence and provenance

**Observed evidence:** The current document set already distinguishes, in spirit, the single decision-log record from Owner-approval claims that appear in other files. There is also an open U-1 matter for several approval claims.

**Existing document content:** The relevant separation already exists in the current framing. What is proposed is an explicit status label and convention on top of that existing separation.

**Team/agent proposal:** The authorization-claim status label is an agent/team proposal, informed by the existing separation discipline and by the fact that U-1 is still open for several claims.

### 8. Unresolved questions

- Should the label describe only the state of verification, or also suggest what should happen next?
- Who is responsible for verifying a claim once it is so labeled?
- Does the project need a standard phrase, or would a clear explanation in each case be enough?

## R-05 — External-condition-evidence model treatment

**Related boundary:** B9 (what external-condition evidence does and does not establish).

### 1. Original proposal

The working model should explicitly distinguish the condition itself, the evidence that the condition existed, the time the evidence was observed, the source and provenance of that evidence, and any effect on a prior decision or authorization. Unknown provenance should stay unknown. A screenshot of a login page is not proof of successful authentication. In Task 8.8.8 this is labeled F-05.

### 2. Plain-language explanation

Sometimes the project needs to talk about something that happened outside the repository, such as whether a service was reachable, whether a login worked, or whether some external condition was true at a certain time. The evidence for those things is different from the things themselves.

The proposal is to give that kind of evidence its own model treatment, so the project does not accidentally over-read a piece of external evidence as stronger than it is, or under-read it as if it were irrelevant.

### 3. Concrete example

A screenshot of a login page shows that a login page was reachable at some moment. It does not, by itself, prove that a real person successfully authenticated, that a session was established, or that any later action was actually authorized.

If that screenshot is later summarized as "the system was accessible and working," the summary may be stronger than the evidence supports. If, on the other hand, the screenshot is ignored entirely because it is "only a screenshot," the project may lose a useful piece of evidence whose limits are clear.

The point is not that screenshots are useless. The point is that a screenshot is evidence of a limited and specific kind.

### 4. Proposed treatment

If adopted, the model would define what external-condition evidence can and cannot establish, and what accompanying details should be recorded, such as when it was observed and how. Unknown provenance would remain unknown rather than being filled in later.

### 5. Consequences of adoption

**Possible benefits:**
- Clearer limits on what external evidence proves.
- Less chance of reading a login screenshot as proof of successful authentication.
- Better handling of evidence whose meaning depends on when it was observed and from what source.

**Complexity and operational impact:**
- The project would need to decide how to record and discuss this kind of evidence consistently.
- Not every external observation would fit neatly into a model rule.
- People would have to think about evidence quality explicitly, which can be slower than ad hoc summaries.

**Possible risks:**
- The model rule could make the evidence seem more formal or structured than it really is.
- If the rule is too strict, useful external evidence may be under-used.
- If the rule is too loose, the original problem returns.

### 6. Consequences of rejection or deferral

**If rejected:** the project continues to treat external-condition evidence case by case. That can still be workable, but the limits of each piece of evidence depend on the care of the person writing the summary.

**If deferred:** the issue is postponed until a real case makes the need clearer.

**What remains unresolved either way:** whether the project benefits enough from a formal treatment to justify the added discipline.

### 7. Evidence and provenance

**Observed evidence:** There is a real external-condition-evidence observation related to the Shopee login screenshot. The observation is real; the proposed model category is not.

**Existing document content:** The corrected framing already treats that observation as evidence of a limited kind rather than as operational proof.

**Team/agent proposal:** The explicit B9 concept is an agent/team proposal. The observation that motivates it is real; the model treatment is proposed.

### 8. Unresolved questions

- How formal does the treatment need to be before it is useful?
- Should the model say what conclusions the evidence may support, or only what must be recorded alongside it?
- Is this a general model rule, or a rule that only matters for a few specific kinds of external evidence?

## R-06 — Partial supersession naming and validation bar

**Related boundary:** B10 (a later Owner decision superseding only part of an earlier authorization).

### 1. Original proposal

The working model should explicitly allow the possibility that a later Owner decision supersedes only part of an earlier authorization, without assuming that it replaces the entire earlier scope. In Task 8.8.8 this is labeled F-06.

This is currently a proposed concept. It is not a demonstrated case.

### 2. Plain-language explanation

Sometimes a later decision changes a previous decision, but not all of it. The later decision may replace one piece while leaving the rest untouched. If the model has no way to describe that, people may either overstate the change as a complete replacement, or avoid dealing with partial-scope changes when they actually happen.

The proposal is to name this possibility explicitly in the working model.

### 3. Concrete example

Imagine that an earlier authorization covered a broad scope, and later an Owner decision changes only one part of that scope. If the project has no way to say "this part is superseded, that part is not," then either the whole earlier authorization gets treated as replaced, or the partial change gets handled informally and ambiguously.

The risk is not that partial supersession definitely happened in the current set. The risk is that, if it does happen later, the project may not have a clear way to describe it.

This example is illustrative; it is not presented as an established case from the current record.

### 4. Proposed treatment

If adopted, partial supersession would become an explicitly named possibility in the model, with some defined level of evidence needed before it would be treated as validated.

### 5. Consequences of adoption

**Possible benefits:**
- The model would have a way to describe partial-scope changes without forcing a whole-scope restatement.
- Future cases may be recorded more precisely.
- The project would have a clearer expectation about what counts as evidence for partial supersession.

**Complexity and operational impact:**
- Defining "partial" precisely may be harder than it first appears.
- The project would need to decide when partial supersession is real and when a change is better described in some other way.
- If the validation bar is unclear, the concept may be applied too freely or not at all.

**Possible risks:**
- There is a real risk of treating partial supersession as validated when it has not been demonstrated.
- The concept could be used to overcomplicate changes that are better described as a simple replacement.
- A poorly defined bar could make the model look more precise than the actual decisions support.

### 6. Consequences of rejection or deferral

**If rejected:** partial supersession remains an open question rather than a named capability. The project would still have related governance rules, but not a dedicated concept for partial-scope changes.

**If deferred:** the concept is postponed until there is either a real verified case or clearer agreement about what would count as evidence.

**What remains unresolved either way:** whether partial supersession is a real future need, and if so, how much evidence should be required before treating it as validated.

### 7. Evidence and provenance

**Observed evidence:** There is no current in-set case that demonstrates partial supersession of an authorization scope.

**Existing document content:** There is a related governance rule, for example the idea that a formula must not be changed retrospectively without an explicit Owner decision; that is a change-discipline rule, but it is not the same as a demonstrated partial supersession of authorization scope.

**Team/agent proposal:** The B10 concept is an agent/team synthesis. The existing governance rule is real; the partial-supersession concept itself is not validated by the current set.

### 8. Unresolved questions

- Is partial supersession a likely real need, or mainly a theoretical possibility?
- What would count as sufficient evidence to treat partial supersession as validated rather than merely possible?
- Should the model name the concept now and leave validation for later, or wait for a real case before naming it at all?

## R-07 — `RELATED — LINKAGE NOT ESTABLISHED`

**Related boundary:** B11 (recording a real relationship without claiming it is a verified linked chain).

### 1. Original proposal

The working model should adopt an explicit status for cases where implementation, evidence, requirement, or authorization records are related in a real sense but are not yet verifiable as one linked chain. In Task 8.8.8 this is labeled F-07. The proposed exact phrase is "RELATED — LINKAGE NOT ESTABLISHED."

### 2. Plain-language explanation

Sometimes two things genuinely relate to each other, but the project cannot yet show the full chain of linkage between them. For example, one record may be about a topic that another record also touches, but there is not enough evidence to say they form one verified chain.

The proposal is to have a fixed phrase for that situation, so the relationship is neither denied nor overstated.

### 3. Concrete example

Imagine that a measurement formula is approved, and the project also plans to start an experiment later. Those two things are related in the sense that both belong to the same effort. But approval of the formula does not, by itself, establish that the experiment has started or that the approval chain for the experiment is complete.

Without a fixed phrase, a later summary might narrate the relationship as if it were a fully verified chain, or it might leave the relationship so vague that the missing linkage is hard to see. The proposed phrase is meant to say: the relationship is real enough to mention, but the linkage is not yet established.

This example illustrates the intended use of the phrase; it is not being presented as a claim that any particular existing record is mislabeled.

### 4. Proposed treatment

If adopted, the project would use the fixed phrase, or some approved equivalent, to flag related-but-not-yet-verified relationships in a consistent way.

### 5. Consequences of adoption

**Possible benefits:**
- A consistent way to describe relationships that are real but not yet verified as a linked chain.
- Less chance of later writing that quietly turns a loose relationship into a claimed verified chain.
- Easier review, because the gap is named rather than left implicit.

**Complexity and operational impact:**
- The exact phrase and its meaning would need to be agreed on.
- People would need to decide when the phrase applies and when a relationship is either strong enough to call linked or too weak to call related at all.
- The phrase must be used carefully so it does not become a catch-all for unclear situations.

**Possible risks:**
- A fixed phrase can harden an informal status into a false sense of precision.
- If used too freely, the phrase may become meaningless.
- If used too reluctantly, the original problem returns.

### 6. Consequences of rejection or deferral

**If rejected:** the project continues to describe related-but-not-verified chains informally. That can still work, but the wording may be less consistent.

**If deferred:** the issue is postponed until the project sees whether a standard phrase is actually helpful.

**What remains unresolved either way:** whether the project benefits enough from a fixed phrase to justify adding it, and whether the chosen phrase will stay meaningful in practice.

### 7. Evidence and provenance

**Observed evidence:** The related idea already appears in spirit in existing separation clauses, including the sense that a formula approval does not, by itself, start the experiment.

**Existing document content:** Existing documents show the underlying separation in several places. The exact proposed phrase is not yet established as a working convention in the current document set.

**Team/agent proposal:** The exact phrase and its status as a working-model convention are an agent/team proposal.

### 8. Unresolved questions

- Is the exact phrase "RELATED — LINKAGE NOT ESTABLISHED" the right wording, or is some other wording better?
- Should the status apply only when there is a real relationship, or could it also be used more broadly?
- Does the project need this as a standard convention, or only as a useful label in a few cases?
