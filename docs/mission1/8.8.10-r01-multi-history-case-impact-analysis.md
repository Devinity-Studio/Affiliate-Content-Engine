## 1. Executive summary

R-01 asks whether the working model should contain an explicit way to say that one source or event may contribute to more than one history, while keeping each history's meaning, provenance, and status distinct.

The core insight is simple: **a single thing can matter to several different lines of thought at once without making those lines of thought the same thing.** That is a real phenomenon. The question R-01 raises is whether the model should say that explicitly, or whether the current practice of separating things by labels, fields, and document status is enough.

The analysis below finds that:
- The current documents already separate several kinds of meaning in practice.
- They do **not** currently implement an explicit multi-history-contribution convention such as H-INTENT/H-UND/H-REQ/H-AUTH tagging or any history-contribution metadata field.
- The four-history vocabulary itself currently lives in conversation-level working material and in task reports, not in a ratified model-definition file in `docs/mission1/`.
- There are real illustrative situations where one source could touch more than one history, and where imprecise wording could blur the boundaries that the project currently tries to protect.
- Whether that gap matters enough to justify a new explicit convention is a decision for the Owner, not something this analysis resolves.

## 2. Plain-language explanation

### 2.1 What "one source contributing to more than one history" means

Imagine a single public web page that describes a Thailand affiliate program's commission terms.

That page is one thing.

Now imagine three different uses of that page:
- Someone reading it to understand how the program seems to work.
- Someone citing it to support a sentence in a draft script.
- Someone treating it as background for a measurement assumption before the experiment begins.

All three uses come from the same source. But they are not the same use.

In the language used by this project's working model, the four-history vocabulary is:
- **H-INTENT** — goals, direction, rationale, evolving intent.
- **H-UND** — agent/team interpretations, assumptions, mistakes, corrections, understanding.
- **H-REQ** — expected behavior and approval status, including requirement-like statements.
- **H-AUTH** — explicit Owner authorization.

The point of R-01 is not that every source must produce four entries. It is that a single source might legitimately relate to more than one of these histories at the same time. For example, one document might inform understanding and also be cited by a requirement-like statement and also be relevant to intent discussion, with each relationship kept separate.

### 2.2 The real question

The real question is not "can one thing matter in more than one way?" The answer to that is obviously yes.

The real question is: **does the project need an explicit model convention for that, or is it already handling it adequately through existing labels, fields, and document structure?**

That is the decision R-01 is really about.

### 2.3 What R-01 is trying to prevent

R-01 is trying to prevent three kinds of drift:

1. **Structure mistaken for mechanism.** The documents may already separate things by labels and status. The risk is that people later talk as if that structural separation already proves the model can explicitly express a multi-history contribution. It does not prove that.

2. **Meaning merger.** If one source is relevant in several contexts, there is a risk that later summaries quietly treat those contexts as if they were a single unified conclusion, when they are not.

3. **Authority transfer by proximity.** A source's presence in one history must not automatically transfer authority into another. For example, something that helps the team understand a topic must not automatically become a requirement, and something documented as a requirement must not automatically become Owner authorization.

These are the practical hazards R-01 is trying to make visible.

## 3. Concrete illustrative scenarios

The following three scenarios are **illustrative examples**, not historical evidence. They are constructed to show the shape of the issue, not to assert that any specific past case occurred in exactly this way.

### Scenario 1 — One source contributing to both Owner Intent and team/agent Understanding

**Source or event (illustrative):** a public affiliate-program guide that describes how commission statuses are labeled.

**Possible interpretation (illustrative):** a reader concludes the guide suggests that one status means "paid" while another means "confirmed," and notes that the program's wording looks plausible for planning.

**Relevant histories (illustrative):**
- Intent-like discussion: "this program may fit the kind of workflow we are planning."
- Understanding-like record: "this is how the guide describes the statuses; here is what we infer and what we do not infer."

**What is established (illustrative):** the guide existed, and the project had access to it at some point. The project can record what the guide appeared to say.

**What remains uncertain (illustrative):**
- Whether the guide's wording means exactly what the reader thinks it means.
- Whether any Owner intent should be inferred from that guide.
- Whether a later decision should be bound by that reading.

**What must not be inferred (illustrative):**
- That understanding of the guide is the same thing as Owner intent.
- That a plausible reading in an understanding record is an approved direction.
- That access to the source at one time is proof the source remains accessible or remains authoritative later.

**Why this is a multi-history question:** the same source may inform both an intent discussion and an understanding record, but the two records serve different purposes and carry different authority. They should not be collapsed into one just because the source is the same.

### Scenario 2 — One source relating to Requirement and Authorization without conflating them

**Source or event (illustrative):** a planning document that states a desired workflow rule or acceptance condition.

**Possible interpretation (illustrative):** the document says the project should capture commission statuses in a disciplined way and should keep pending/rejected amounts out of confirmed net income.

**Relevant histories (illustrative):**
- Requirement-like content: "this is what the workflow should do or what the record should track."
- Authorization-like content: "the Owner has approved or not approved the concrete change that would make this real."

**What is established (illustrative):** the requirement-like statement exists as a documented idea. That is meaningful.

**What remains uncertain (illustrative):**
- Whether the Owner has separately authorized the implementation or operational change that would enact it.
- Whether the documented rule is already in force or still a proposal.
- Whether a requirement-like statement in one document is the same as a decision that has been approved through the relevant gate.

**What must not be inferred (illustrative):**
- That a documented requirement-like statement is automatically an authorized action.
- That an authorization record is automatically the same as the full scope of a requirement.
- That implementation or testing of something is the same as having been authorized to do it.

**Why this is a multi-history question:** the same underlying topic can appear as a requirement-like statement and also as an authorization question, and those are not the same history. A multi-history-aware model would need to keep those distinct even when the topic is shared.

### Scenario 3 — A source whose multi-history contribution is uncertain or not yet established

**Source or event (illustrative):** an external resource that the project references, but whose exact meaning, accessibility, or provenance is not fully settled.

**Possible interpretation (illustrative):** the project says the resource "seems relevant" or "is cited as a normalization model" or "is referenced but not independently verified."

**Relevant histories (illustrative):**
- Evidence/understanding: "this is what the source appears to say, with these limits."
- Possible intent or requirement influence: "this may bear on a later decision, but that influence is not yet established."

**What is established (illustrative):** the project can record the existence of the reference and what it appears to support, with the limits clearly stated.

**What remains uncertain (illustrative):**
- Whether the source is currently accessible.
- Whether the source has been independently verified.
- Whether the source should influence intent, requirements, or authorization in any specific way.
- Whether the source contributes to more than one history in a meaningful, documented sense.

**What must not be inferred (illustrative):**
- That a reference implies verification.
- That an inaccessible source is the same as no source.
- That a referenced source is part of a verified decision chain.
- That uncertainty about contribution means the source has no value at all; it may still be useful evidence of a limited kind.

**Why this is a multi-history question:** in uncertain cases, the project may not yet know whether the source truly contributes to more than one history. A good treatment would be able to say both "this source may be relevant in several ways" and "we have not established that it does."

## 4. Existing-documentation findings

This section reports what the current documents do and do not provide. It is a documentation inspection, not a claim that the model is already implemented.

### 4.1 Explicitly documented support

The current document set explicitly separates several things that are closely related to the multi-history idea:

- **G1 and G2 are kept distinct.** This separates plan direction from experiment gating. That separation is one of the strongest in the set. It is consistent with the idea that one line of work does not automatically become another.
- **Production and G3 approval are kept distinct.** That keeps working steps separate from approval gates.
- **M1/M2 measurement discipline and the not-yet-measurable rule are kept distinct.** That keeps interpretation and cash status separate.
- **Draft/disclosure discipline in I and J is preserved.** That keeps team-understanding drafts separate from implementation and Owner intent.
- **Implementation note M is kept outside acceptance/authorization.** That keeps implementation evidence from being mistaken for approved requirements or authorization.
- **Term-sense discipline for `profile_bio` is preserved.** That keeps a planning vocab term from being silently merged with an external concept.

In other words, the documents already do a lot of separation work that is closely related to the spirit of R-01.

### 4.2 Partial support through labeled fields or conventions

The documents also support the multi-history idea in a partial, structural way:

- **Separate labeled fields exist.** For example, G uses separate labeled parts for different kinds of content, and D §3.3 defines separate fields such as `hypothesis`, `success_criteria`, `commission_assumption`, and `observation_schedule`.
- **Separate gate stages exist.** B defines distinct stages, with Stage 2 placed before G1 and Stage 3 gated by G2. That separation is one concrete way the set already handles the idea that one activity is not automatically the next.
- **Separate decision and measurement records exist.** G §2a and §2b keep distinct records and keep the measurement-formula approval separate from starting Experiment 1. G §2b L90 explicitly says the formula approval does not start Experiment 1.
- **Status labels exist.** Draft/approval/implementation statuses are used to keep categories distinct.

This is real support for the **spirit** of R-01. It shows the project already has many reasons to keep things separated.

### 4.3 Missing or unclear support

What is missing is an **explicit multi-history-contribution convention**.

Specifically:
- No existing file implements H-INTENT/H-UND/H-REQ/H-AUTH tagging.
- No existing file implements a history-contribution metadata convention.
- The four-history vocabulary is not currently implemented as a labeled taxonomy in any inspected file.
- The four-history model does not exist in `docs/mission1/` as a ratified model-definition file. It currently resides in conversation-level working material and in task reports such as 8.8.5 and 8.8.7.

This does **not** mean the underlying separation is absent. It means the separation is structural and conventional rather than expressed through an explicit multi-history mechanism.

### 4.4 Proposed future capability

R-01 is the proposed capability. In the current state:
- The underlying idea is supported by existing separation discipline.
- The explicit mechanism is a proposal, not an established feature.
- The proposal is that the model should acquire an explicit way to say that one source or event contributes to more than one history while keeping each contribution distinct.

This is the same distinction made in 8.8.9 packet R-01 and in 8.8.8 F-01: the current separation is real; the explicit mechanism is proposed.

### 4.5 A precision note on the four-history vocabulary

It is worth saying plainly what is and is not present:

- **Present:** the four-history vocabulary is part of the working model discussions and task reports.
- **Present:** the project uses many labels, fields, and status conventions that separate meaning in practice.
- **Not present:** an explicit, implemented, file-backed four-history tagging system or history-contribution metadata convention.

This matters because R-01 is partly about whether the absence of that explicit mechanism is a real gap or just a feature of how the model is currently expressed.

## 5. Comparison of three possible treatments

This section compares three treatments. It does not choose one.

### 5.1 Option 1 — Continue with labeled separation

**What it is:** keep the current approach of distinguishing histories through explicit labels, fields, provenance notes, and document status.

**What it solves:**
- It preserves the separation the project already has.
- It avoids adding a new convention, field, or mechanism.
- It continues to rely on the existing discipline that already distinguishes G1 from G2, production from G3, M1 from M2, drafts from implementation, and so on.

**What it does not solve:**
- It does not give the model an explicit sentence or convention for "this one source/event contributes to multiple histories."
- It leaves open the risk that someone may later mistake structural separation for an explicit multi-history mechanism.
- It depends on continued discipline and careful reading rather than an explicit rule.

**Complexity introduced:**
- Very little new complexity. This is mostly continuity.

**Risks:**
- The main risk is retrospective blur: later summaries may speak as if multi-history handling is an operational feature simply because the documents are separated by labels.
- Another risk is inconsistent future writing if discipline slips.

**When it may be appropriate:**
- When the current separation is actually working well enough for real cases.
- When the project wants to avoid adding machinery before there is a demonstrated need.
- When the main concern is preserving what already exists rather than creating a new way to express shared contributions.

### 5.2 Option 2 — Define an explicit conceptual convention

**What it is:** define how one source may contribute to multiple histories while keeping each contribution distinct, without necessarily specifying a schema or implementation. This is the direction R-01 points toward if the Owner wants something more explicit than Option 1.

**What it solves:**
- It makes the multi-history idea expressible as a model concept, not just a pattern people might notice.
- It reduces the chance of confusing "documents happen to be separated" with "the model can explicitly express shared contributions."
- It can give writers and reviewers a common way to talk about the issue.

**What it does not solve:**
- It does not automatically tell you which sources really do contribute to multiple histories; that still has to be judged case by case.
- It does not by itself prevent misuse unless the convention is written and applied well.
- It may still leave open questions about concreteness: what exactly counts as a contribution, and how strong the statement must be.

**Complexity introduced:**
- Some definitional work would be needed: what counts as a contribution, what counts as distinct, what language or convention would be used.
- People would need to learn and apply it consistently.
- There is a real danger of over-formalizing a concept that may only need occasional careful wording.

**Risks:**
- If the convention is too concrete, it may later be mistaken for an implemented mechanism.
- If it is too vague, it adds wording without much usable meaning.
- If it is drafted carelessly, it could encourage over-claiming that a source "contributes" where the evidence does not support it.

**When it may be appropriate:**
- When the Owner wants the model to be able to say the multi-history relationship explicitly.
- When the project expects this issue to recur and wants a shared vocabulary for it.
- When the Owner is comfortable with a conceptual convention that may still need future refinement.

### 5.3 Option 3 — Defer the mechanism

**What it is:** keep B5 as a boundary principle or observation, and wait for a real case that demonstrates the need for a more explicit convention.

**What it solves:**
- It avoids inventing a mechanism before there is a clear practical driver.
- It keeps the model simpler until a real case forces more precision.
- It preserves the current separation without committing to a new convention now.

**What it does not solve:**
- It does not answer whether the current separation is sufficient in principle.
- It may leave the project with informal wording if and when the issue becomes important.
- It may make later adoption harder if the need only becomes visible after several documents have already drifted.

**Complexity introduced:**
- Little now; possible later cleanup if the issue becomes more visible later and the project has already built up inconsistent wording.

**Risks:**
- If a real case eventually shows the current separation is not enough, the project may need to retrofit the convention into already-written material.
- If the need is real but delayed, deferral can quietly become de facto rejection unless someone reopens the question.

**When it may be appropriate:**
- When there is no strong current case and the Owner prefers evidence before committing to a convention.
- When the Owner thinks the issue is real but not yet important enough to standardize.
- When the main value of the proposal is preventive and the Owner would rather wait for a concrete trigger.

## 6. Validation requirements

The following are proposed validation questions. They are not authorization to implement tests, records, or code. They are a way to think about what would have to be true for any explicit multi-history convention to work as intended.

### 6.1 Preserving the original source

An explicit convention would need to keep the original source or event identifiable and unchanged, so that later interpretations do not silently rewrite what the source was.

A useful validation question is: **if the source is later re-read or re-cited, can the project still tell what the original source was and how it was originally recorded?**

### 6.2 Keeping different interpretations distinct

The convention would need to keep separate interpretations from collapsing into one another just because they came from the same source.

A useful validation question is: **if two interpretations disagree, does the convention keep them visibly distinct rather than merging them into a single conclusion?**

### 6.3 Preventing Intent from becoming Requirement automatically

A multi-history convention should not allow something recorded as intent or direction to automatically become a requirement.

A useful validation question is: **does the convention preserve a visible gap between "this was part of intent/discussion" and "this is a requirement-like statement," even if both touched the same source?**

### 6.4 Preventing Requirement from becoming Authorization automatically

A multi-history convention should not allow a requirement-like statement to automatically become Owner authorization.

A useful validation question is: **if the model records a requirement-like statement and a separate authorization statement, does it remain clear that one does not equal the other?**

### 6.5 Preserving provenance and verification status

The convention would need to keep provenance and verification status attached to each interpretation, not just to the source as a whole.

A useful validation question is: **can the model say that the source was used in one way with one verification status, while another use of the same source has a different or unknown verification status?**

### 6.6 Handling uncertain or disputed interpretations

The convention should be able to represent uncertainty without forcing a false conclusion.

A useful validation question is: **can the model say "this source may relate to more than one history, but we have not established the strength or scope of those relationships"?**

### 6.7 Correcting one interpretation without silently changing unrelated interpretations

If one interpretation is later corrected, the correction should not silently rewrite other interpretations that used the same source.

A useful validation question is: **can a correction in one history be made without implying that every other history using the same source is also corrected?**

## 7. Unresolved questions

- Is the current labeled separation sufficient for the project's actual needs, or is an explicit multi-history convention really necessary?
- If an explicit convention is wanted, should it be a conceptual rule only, or should it eventually become a more concrete record or metadata convention?
- Does the current document set already handle the most important multi-history risks well enough, with the main remaining issue being wording discipline rather than missing mechanism?
- How would the project tell the difference between a source that genuinely contributes to multiple histories and a source that merely touches several conversations without real shared contribution?
- Does deferring the mechanism create a meaningful risk of later inconsistency, or is that risk small enough to wait for a real case?

These questions are left open on purpose. They are decision inputs, not decisions.
