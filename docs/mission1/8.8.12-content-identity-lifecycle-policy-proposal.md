# 8.8.12 — Content Identity & Lifecycle Policy Proposal

**Document:** `docs/mission1/8.8.12-content-identity-lifecycle-policy-proposal.md`
**Purpose:** Establish clear operational meanings for five content operations before any Content Lineage implementation.
**What this is:** A documentation-only policy proposal.
**What this is not:** Authorization, implementation, schema, migration, or a decision that content lineage should be built.

---

## 0. Basis for this proposal

This proposal is based on the implementation facts gathered in Task 8.8.11 and the same read-only inspection of the current codebase. It does not assume any capability that the inspected code does not show.

It also treats the assistant's recommended boundaries from 8.8.11 as recommendations only. They are useful starting points, but they are not Owner authorization and they do not change the current implementation.

The four principles that constrain everything below are:

- **Content Project is the working source of truth.** The export index is downstream from it.
- **Editing and re-exporting a project do not automatically create a new Content identity.**
- **If a derived copy or a "new version of the same content" capability is added, its identity rules must be declared explicitly, not inferred from file names.**
- **A re-export does not guarantee that the previous exported file still exists.** Whether the prior file survives depends on whether the new export produces the same filename or a different one, because the current render path can overwrite an existing file.

---

## 0A. Why this corrected draft exists

The earlier draft said, in effect, that the previous exported file stays on disk unless something explicitly removes it. That assumption is not reliable for the current implementation.

The current code is closer to this:

- The exported file destination is built from `content_id` and `script_version`, for example `<exports-dir>/<content_id>/<content_id>-v<script_version>.mp4` (`app/mvp/content.js`, `exportProject()`).
- The render tool is invoked with ffmpeg's overwrite flag `-y`, so writing to an existing destination file is allowed (`app/remotion/render.js`, `renderVideo()`; `app/mvp/content.js` still capture pass).
- The Content Library entry for an export is keyed by `id` plus `filename`. When a re-export produces the same id and filename, the old record for that filename is removed from the index and replaced with the new one before the index is written (`app/mvp/content.js`, library write path).

So the real question for lifecycle is not "is the old file still there?" The real question is "did this re-export produce the same filename or a different one?". If the filename is the same, the prior file is replaced and the prior library record for that filename is replaced. If the filename is different, both files can exist at the same time and the library can reflect a different export for the same content project.

This matters because a policy that assumes old exports are always preserved would be wrong for the current implementation. The corrected draft below removes that assumption and adds a concrete re-export case analysis.

---

## 1. Plain-language summary

ACE currently has three things it can do with content:

1. **Edit the current working copy** of a content project, keeping the same content id.
2. **Export the current working copy** to a real MP4 file, and record that export in the Content Library index.
3. **Create a new content project** from a saved or queued candidate.

It does **not** currently have a declared operation that means "make a copy of this content that is intentionally related to the original" or "make a new version of this same content item."

That missing distinction is the main reason this proposal exists. Without it, three very different situations can look the same to anyone reading the repository:

- "I fixed a typo in the working copy."
- "I made a new independent piece of content for a different channel."
- "I wanted a copy of this content but with one deliberate change."

All three are real workflows that ACE may need. They are not the same thing. This proposal draws the lines between them before any code that would act on the lines is written.

## 2. The five operations

### Operation 1 — Edit an existing Content Project

**Plain language:**

You take the content project that already exists and change something in it: a scene, a line of text, an audio asset, the ordering of scenes, or another working value. The content id stays the same.

**Exists in current implementation?**

Yes.

**What identity is preserved:**

- `content_id`
- `product_id`
- `candidate_id`
- `offer_id`
- `shop_id`
- `plan_id`
- `plan_record_id`
- `approach`
- `source_ids`
- `evidence_ids`
- `offer_snapshot`
- The relationship to the same content project object in state

**What happens to previous work:**

- Previous in-memory states are not preserved as separate project objects.
- `edit_log` keeps a sequence of change events.
- If script text changes, `script_version` may increase and a new `script_version_history` entry is recorded.

**What happens to exported files:**

- Nothing, unless you re-export.
- Editing does not regenerate the exported file. If there was a previous export, it remains whatever the last export produced.

**What history is retained:**

- Edit events in `edit_log`.
- Script version history entries when script text changes.
- The provenance note and offer snapshot that were attached at creation time.

**What can currently be proven:**

- That the project was edited at a particular time, with a particular change description and possibly a particular track or scene id.
- That the script version and content version moved to a new state.
- That the exported file, if any, still reflects the file that was produced at the time of export.

**What remains unknown or unsupported:**

- Whether an edit is "the same content, just improved" versus "a change significant enough to deserve a new lineage note."
- Whether an edit should ever invalidate a prior export as the object of record, even if the file itself still exists.
- Whether an edit is tied to any particular decision history. The data does not say that.

**Concrete example:**

Content A has `content_id: CNT-1`. You change one text line in scene 3. The content id is still `CNT-1`. `storyboard.version` or `script_version` may increase. `edit_log` records the change. The previous export file, if any, is untouched by the edit itself.

### Operation 2 — Export an existing Content Project again

**Plain language:**

You ask the system to render the current content project to a real video file again. What happens to the previous exported file depends on the filename, not on the fact that this is a re-export.

In the current implementation, the exported file is named from `content_id` and `script_version`, and the render pass uses ffmpeg's overwrite flag. That means:

- If the re-export produces the same filename as before, the prior file is overwritten.
- If the re-export produces a different filename, both files can exist at the same time.

A re-export is a rendering event. It is not automatically a new content identity.

**Exists in current implementation?**

Yes.

**What identity is preserved:**

- `content_id`
- The project's relationship to its candidate, offer, product, plan, sources, and evidence
- The fact that the export comes from this project in state

**What happens to previous work:**

- The content project continues to be the same object.
- The previous export file is not automatically kept as a separate file. If the filename is the same, the old file is replaced.

**What happens to exported files:**

- The output file is written under `exports/<content_id>/` with the naming convention `<content_id>-v<script_version>.mp4`.
- A still frame and render metadata may be produced too.
- The Content Library entry keyed by `id` and `filename` is replaced before the index is written, so a same-name re-export updates the library record rather than preserving two entries for the same filename.

**What history is retained:**

- The new export's file, sha256, and creation metadata.
- The project's edit log and script version history, if relevant.
- The library entry recording the export's integrity data.

**What can currently be proven:**

- That this specific file was produced from this specific project at this specific script version.
- That the file's actual bytes match the recorded sha256 when retrieved from the library.
- That the exported file is linked to the content project id.

**What remains unknown or unsupported:**

- Whether a re-export should be treated as "the same content item, just refreshed" or as a new exported variant that should be trackable alongside the prior variant.
- Whether the library should keep one entry per content id, one entry per export, or some other rule. This proposal does not decide that.
- Whether an exported variant is part of a declared lineage chain. It is not, in the current model.

**Concrete example:**

Content A is `CNT-1`. If you re-export without changing the script version, the filename is the same as before, so the previous exported file at that path is overwritten and the library record for that filename is replaced. If you first bump the script version and then re-export, the filename changes to `CNT-1-v2.mp4`, so the previous file `CNT-1-v1.mp4` can remain on disk while the new file is created separately.

### Operation 2A — Re-export cases that matter for lifecycle

This is the case analysis you asked for. It uses the same export behavior described above.

**Case 1 — Re-export with no script change**

- The content project is the same.
- The script version is the same.
- The export filename is the same as before.
- The render passes `-y` to the same destination file, so the old exported file is overwritten.
- The library entry for that filename is replaced with the new export record, including the new sha256.

What this means:

- There is still one content project, `CNT-1`.
- There is not automatically a second file kept for "the old export."
- The old sha256 is no longer in the library unless something else preserved it separately.
- A script version history entry or an edit log may already exist if the re-export was triggered after an edit, but the export itself does not create a new content id.

**Case 2 — Re-export after a script change**

- The content project is the same.
- The script version has changed.
- The export filename changes too, for example from `CNT-1-v1.mp4` to `CNT-1-v2.mp4`.
- A new exported file is created.
- The old exported file can remain on disk, because it is a different filename.

What this means:

- The library may now hold a record for the newer filename.
- The older file may still exist, but the library does not automatically keep a record for every old filename forever unless the policy says so.
- This is the case that looks most like "we have two versions" to a human, but the system still treats them as two exported files tied to one content project, not as two separate content identities.

**Case 3 — Re-export after a change that does not bump script version**

This covers edits or state changes that do not increase `script_version`.

- The export filename may be the same as before.
- The old exported file can be overwritten.
- The old library record for that filename can be replaced.

What this means:

- Two different things can be true at once: the project changed, but the export filename did not change.
- That is exactly why script version and exported-file history are not the same thing. A project can change without producing a new export filename, and a re-export can overwrite a file even when the project changed a little.

**Case 4 — Effect on the file and the library entry**

The two artifacts behave differently:

- **Exported file:** replaced only if the new export writes the same filename. Not replaced just because the project changed.
- **Library entry:** replaced by a new export if the id and filename match. The library is updated as part of export, not as a separate library-edit operation.

What this means:

- If the goal is to preserve an old exported file, the current system does not do that automatically just because the file existed before.
- If the goal is to preserve an old library record, the current system does not do that automatically either, because a same-name re-export replaces the record for that filename.

### Operation 3 — Create a new independent Content Project

**Plain language:**

You start fresh content from a saved or queued candidate, optionally through a plan. You get a new content id, a new edit log, a new script version 1, and a new offer snapshot. The new project is not declared to be a copy of anything else.

**Exists in current implementation?**

Yes.

**What identity is created:**

- A new `content_id`, allocated as `CNT-N` from the current content count.
- A new project object in `state.contents`.
- A new edit log.
- A new script version history starting at version 1.

**What happens to previous work:**

- The new project is independent of any existing content project object.
- It does not inherit the prior content project's edit log, current scene state, or current script version.
- It may share the same candidate, offer, or product if the same source was chosen, but that is a shared source of data, not a declared lineage relationship between content items.

**What happens to exported files:**

- There is no initial export. A new content project must be finalized and exported separately if an export is needed.

**What history is retained:**

- The new project's own creation provenance and limitations.
- The new project's own edit log and script version history going forward.
- Whatever source/evidence ids were attached at creation.

**What can currently be proven:**

- That a new content item was created at a certain time from a certain candidate/plan context.
- That it began at script version 1.

**What remains unknown or unsupported:**

- Whether the new project was intended to be "independent but related" to some existing content.
- Whether the new project is a deliberate variant, a clean restart, or just another item for a different channel.
- Any "created because of" relationship between projects.

**Concrete example:**

You create Content B from a different candidate, or from the same candidate but as a separate project. It becomes `CNT-2` with its own blank edit log. It has no declared relationship to `CNT-1` even if both were built from related offers or the same market area.

---

### Operation 4 — Create a derived copy from an existing Content Project

**Plain language:**

You intentionally make a new content item that is based on an existing one. You want to say plainly that the new item came from the old one, while keeping them as separate items.

**Exists in current implementation?**

Not in the inspected content slice.

**What the current code actually does:**

- There is no dedicated "duplicate content project" operation in `content.js` or in the content workflow handlers in `service.js`.
- There is candidate-level replace/add behavior in the candidate workflow, but that is part of the candidate pipeline, not content lifecycle.
- The only way to start something similar today is to create a new content project from scratch, which does not carry any "based on CNT-X" identity by itself.

**What identity would need to be preserved if this were added:**

- A clear statement that the new item is derived, not independent.
- The source content id.
- The reason for the copy.
- The snapshot of what was copied at copy time, if the system wants to preserve that.
- A rule for whether the copy starts as a draft, a finalized item, or something else.

**What would happen to previous work:**

- The source content project would remain unchanged.
- The new derived item would have its own identity.
- The old export files would remain as they were.

**What history would need to be retained:**

- A derivation record, not just an edit log.
- The source content id and possibly the source export or script version that was copied from.
- The reason and the operator who initiated the derivation.

**What can currently be proven:**

- Almost nothing about this operation, because it does not exist as a declared operation in the inspected slice. You could still create a new content project and then document in the state or in a document that it was inspired by another content item, but that is documentation outside the content model, not a proved system relationship.

**What remains unknown or unsupported:**

- Whether a "derived copy" should create a new content id.
- Whether it should start from the same status as the source or from a default status.
- Whether the copy should copy the offer snapshot, the storyboard, the edit log, or some subset.
- Whether the copy should be able to trace back to a specific export of the source.

**Concrete example:**

You want Content B to start from Content A and then diverge. Today that would require creating `CNT-2` manually and then separately saying somewhere that it began from `CNT-1`. The system does not currently record that as a first-class relationship. If it did, the record would need to say both "B came from A" and "B is now its own item," so later readers do not confuse the two.

---

### Operation 5 — Replace or update an exported Library entry

**Plain language:**

You want the Content Library record for an export to be corrected, refreshed, or replaced. This could happen because the export file changed, because the file was re-rendered, or because the recorded metadata was wrong.

**Exists in current implementation?**

Partially, but only indirectly and not as a general "edit the library record" operation.

**What the current code actually does:**

- The library is written by export through `exportProject()`.
- The library is read by `readContentLibrary()` and `getLibraryItem(id)` in `content.js`.
- `handleContentLibraryItem()` in `service.js` returns the library item and verifies file existence plus sha256 match on retrieval.
- The library is an index, not a user-editable content catalog. There is no separate "edit the library entry's metadata directly" feature in the inspected content slice.
- A same-name re-export replaces the library record for that filename before the index is written, but this happens as part of export, not as an independent library-edit action.

**What identity is preserved:**

- The library id that the export is recorded under.
- The content project id the export came from.
- The export filename, bytes, and sha256 as written by that export.

**What happens to previous work:**

- If the library entry is overwritten or replaced by a new export write, the previous library record is gone from the index, though the prior exported file may still exist on disk if its filename was different.
- If the library entry is simply read and not replaced, nothing changes.

**What happens to exported files:**

- Nothing in the library operation itself changes the exported file. The library only records what the export produced.
- A re-export can indirectly change the library record and can also overwrite the prior exported file, but only if the filename matches.

**What history would need to be retained:**

- If "replace" is allowed, the system should be able to say whether the replacement was a genuine correction of metadata, a re-export, or a manual correction of the index.
- The old sha256 should not be silently treated as if it were the same as the new one.

**What can currently be proven:**

- That a library retrieval either matches the file on disk or reports it as missing/changed.
- That the recorded sha256 is attached to a specific content project id and export filename.

**What remains unknown or unsupported:**

- A generic "edit library metadata" path, if that is even wanted.
- A declared rule for when the library entry is the authoritative record and when it is only a derived record of an export.
- A declared rule for whether replacing the library entry also means replacing the prior export as the official artifact of record.

**Concrete example:**

Content A's export is `CNT-1-v1.mp4`. You re-export and get `CNT-1-v2.mp4`. The new filename is different, so both files can exist. The library may now reflect the newer export. The old file `CNT-1-v1.mp4` may still be on disk. Without an explicit policy, a reader cannot tell from the library alone whether the older file was intentionally kept, intentionally discarded, or simply left behind by the current export write.

If instead you re-export without changing the script version, the filename is still `CNT-1-v1.mp4`, so the old file is overwritten and the old library record for that filename is replaced.

## 4. Current behavior versus recommended behavior

For each operation, the table shows what the current implementation does and what a future policy should say, without promising implementation.

### Operation 1 — Edit existing project

**Current:**

- Mutates the same content project in place.
- Records edits in `edit_log` and script changes in `script_version_history`.
- Keeps the same content id.

**Recommended policy stance:**

- Editing is the normal way to improve the working copy.
- Editing does not, by itself, create a new content identity.
- If an edit is significant enough that the team wants to remember it as a "version of the same content" rather than "one more edit," that should be an explicit decision, not an accident of how the edit was made.

### Operation 2 and 2A/2B — Export again, including the overwrite sub-cases

**Current:**

- Produces an export file named from `content_id` and `script_version`.
- Uses ffmpeg with the overwrite flag, so a same-name export can overwrite an existing file.
- Replaces the library record for the same id+filename when it writes the index.

**Recommended policy stance:**

- Re-export is a rendering action, not a content-identity action.
- A new export file is evidence of a new rendering state, not automatically a new content identity.
- A same-name re-export can replace both the file and the library entry. That is current behavior, not a future one.
- If the project wants to preserve old exports or old library records, that must be a declared retention rule, not an assumption based on "the file used to exist."
- Script version history and exported-file history should be treated as separate things. One is about the working content; the other is about what was successfully rendered to a file at a given time.

### Operation 3 — Create new independent project

**Current:**

- Creates a new content id, new edit log, new script version 1, new offer snapshot.
- Independent object in state.

**Recommended policy stance:**

- This is the correct operation when the new item is genuinely independent.
- If the new item is meant to be related to an older item, the system should have a separate way to say so, not rely on the user remembering to mention it outside the model.

### Operation 4 — Create derived copy

**Current:**

- No declared operation in the inspected content slice.

**Recommended policy stance:**

- If derived copies are in scope, they should be a declared operation with an explicit "based on" relationship.
- A derived copy should keep the source clearly visible but not be treated as the same item as the source.
- A derived copy should not inherit the source's authorization, requirement, or understanding status automatically.

### Operation 5 — Replace/update Library entry

**Current:**

- Library is written by export and read back with integrity checks.
- A same-name re-export replaces the library record for that filename.
- No general library-edit operation in the inspected slice.

**Recommended policy stance:**

- The Library is an export index, not the content source of truth.
- If a library entry is corrected or replaced, the reason should be known and distinguishable: re-export, metadata correction, or manual index repair.
- The library should not silently erase the fact that an older export existed unless there is an explicit retention rule.
- In particular, replacing the library record for a filename is not the same thing as proving that the older file was intentionally retired.

## 5. Concrete lifecycle examples

Use these as the canonical worked examples for this task.

### Example A — Editing and re-exporting one item

1. Content A is created as `CNT-1`.
2. Content A is finalized and exported as `CNT-1-v1.mp4`.
3. A reviewer spots a text issue in scene 3.
4. The team edits scene 3 in the same project. `edit_log` records the change. Script version may bump to 2.
5. The team re-exports. If the script version is now 2, the new file is `CNT-1-v2.mp4`.

At the end:

- There is one content item, `CNT-1`.
- There may be two exported files on disk, but only if the script version changed. If the script version did not change, the re-export overwrites `CNT-1-v1.mp4` instead of creating a second file.
- The edit history is in `edit_log` and possibly `script_version_history`.
- What is not recorded as a first-class fact is whether `CNT-1-v1.mp4` should be considered superseded, retained, or both.

### Example A2 — Re-export without a script change

1. Content A is `CNT-1`.
2. Content A is exported as `CNT-1-v1.mp4`.
3. Something about the project is adjusted, but `script_version` does not increase.
4. The team re-exports.

At the end:

- The filename is still `CNT-1-v1.mp4`.
- The old `CNT-1-v1.mp4` is overwritten by the new render.
- The library record for that filename is replaced with the new sha256 and timestamp.
- This is the clearest case where "re-export happened" and "old file preserved" are not the same thing.

### Example B — Independent new content that looks similar

1. Content A is `CNT-1`, built from candidate X.
2. Later, the team starts Content B from candidate Y.
3. Content B becomes `CNT-2`.

At the end:

- `CNT-1` and `CNT-2` are separate content items.
- They may look similar because the market area is similar.
- The current model can prove each item's own story, but it cannot prove a relationship between them unless someone records it outside the model.

### Example C — A copy you meant to keep related

1. Content A is `CNT-1`.
2. The team wants a variant for a different format or channel and starts from A.
3. Today, that would likely mean creating a new project `CNT-2` by hand and then separately noting that it began from `CNT-1`.

At the end:

- The relationship is not proved by the current content model.
- The result is vulnerable to later confusion: is B a sibling, a copy, a fork, or just another item?

### Example D — Library confusion after re-export

1. Content A exports to `CNT-1-v1.mp4` and is recorded in the library.
2. After a script change, Content A re-exports to `CNT-1-v2.mp4`.
3. A later reader looks only at the library and asks, "Which file is the current one?"

At the end:

- The current implementation can tell you that the library entry matches or does not match the file on disk.
- It cannot, by itself, tell you whether the earlier file was intentionally retired or intentionally kept in case.
- If instead the re-export did not change the script version, the library now points to the newer render under the same filename, and the old file is gone unless something else saved it.

## 6. Risks of ambiguous identity and replacement

### Risk 1 — "Same content" is underdefined

The phrase "same content item" can mean different things in the same sentence:

- same content id
- same script
- same offer
- same video file
- same exported variant

If the policy does not say which one matters, people will answer different questions with the same words.

### Risk 2 — Re-export can overwrite the only surviving copy of an old export

This is the main corrected risk from this draft. A re-export with the same filename replaces the old exported file and the old library record for that filename. The old file is not automatically preserved just because it existed before.

### Risk 3 — Script version history is not exported-file history

A project can have a long script version history and still have only one surviving export file, or even none at all, depending on what was rendered and whether later renders overwrote earlier ones.

### Risk 4 — Edits silently become "new content" in someone's head

An edit keeps the same content id, but a person may still think of the edited result as "the new version." That is a human interpretation, not a system fact. If the system also allowed a new content id for the same kind of change, the two interpretations would collide.

### Risk 5 — Derived copies are invisible without explicit tracking

A copy made from an existing item is easy to lose as a relationship once enough edits accumulate. Without a declared "based on" link, the only evidence is whatever the operator remembers to write down in the state or in docs.

### Risk 6 — Library is not self-explanatory about retirement

Because the library is an export index, it can reflect a sequence of exports without saying which one matters now. That is fine if the project only ever has one export. It is risky if the project can legitimately keep more than one.

### Risk 7 — Approval, understanding, and versioning can be conflated

This is the same family of risk seen in 8.8.10 and 8.8.11. A change to content is not automatically a change to requirement, authorization, or owner intent. If the content operations are ambiguous, the histories around them become harder to keep separate.

## 7. Minimum rules needed before implementing Content Lineage

These are not implementation instructions. They are the minimum policy clarity that should exist before any lineage mechanism is built.

### M1 — Define what "same content item" means

The project needs one agreed definition for "same content item" for lifecycle purposes. Likely candidates:

- same `content_id`, or
- same declared lineage root, or
- some other explicit rule

The definition must be stated before the system can distinguish "edit" from "new version."

### M2 — Define what "new version" means, if it exists at all

If the project wants versioning, it needs to say:

- whether a version is created by editing, by exporting, by an explicit policy action, or by some combination
- what a version is linked to
- whether supersession is automatic or declared

### M3 — Separate "rendering" from "content identity"

Export should be allowed to produce new artifacts without the system pretending that every new file is a new content item.

### M4 — Separate "exported file history" from "script version history"

The current implementation keeps them close together but not identical. Policy should say whether they are allowed to diverge, and what that divergence means.

### M5 — Declare what a same-name re-export is allowed to replace

The project should say, at minimum, whether a same-name re-export:

- replaces the file,
- replaces the library entry,
- both,
- or neither, in which case the system would need a different naming or retention behavior.

### M6 — Define the Library's authority level

The project must say whether the Content Library is:

- a derived export record only, or
- also a place that can be corrected independently, or
- both, with separate rules

### M7 — Define retention for older exports and older library entries

If older exports or older library entries can be kept, the project must say:

- whether they are kept automatically
- whether they can be retired
- who can retire them
- what "retired" means for an export file and for a library entry

### M8 — Define how lifecycle ties to decision history

The project should say, in principle, whether and how a content lifecycle event relates to:

- owner intent
- team understanding
- requirement status
- authorization status

The default should be that content lifecycle does not automatically change those histories.

## 8. Assistant recommendations

### R1 — Keep Content Project as the working source of truth

The current arrangement, where the content project holds the editable state and the library holds the export index, is a reasonable default for this phase.

### R2 — Keep editing as in-place mutation for now

Editing the existing content id is simple and predictable. It also matches the current implementation. Changing that would be a meaningful policy and implementation decision.

### R3 — Treat export as a rendering event, not an identity event

A new export file is an artifact of the current project. It should not automatically create a new content identity.

### R3A — Stop assuming old exports survive a same-name re-export

This is the corrected recommendation. The current code can overwrite the old file and replace the old library record. A lifecycle policy should not promise retention that the implementation does not provide.

### R3B — Keep script version history and export-file history separate in policy

Even when they often move together, they answer different questions. Script version history answers "how did the working content change?" Export-file history answers "what was actually rendered to disk, and what file is the library pointing at now?"

### R4 — Do not introduce "derived copy" unless there is a declared reason

Derived copies are useful, but they add identity complexity. If they are not yet needed on a recurring basis, do not build them yet just to have them.

### R5 — If derived copy is added, make it explicit and small

If it is added, it should at minimum record:

- that it is derived
- the source content id
- the reason
- what snapshot, if any, is copied from the source

### R6 — Keep the Four-History separation as a principle, not as a new content field

Content lifecycle should respect the four-history principle without assuming that content fields are the right place to encode intent, understanding, requirement, or authorization.

### R7 — Do not let file naming become the lineage model

File names can be helpful for humans, but they should not be the only way to tell whether two exports are the same content item, different versions of the same item, or unrelated items.

## 9. Items that genuinely require Owner authorization

These are not technical details. They are policy questions that should be answered by the Owner, not by the assistant.

1. Whether content lineage is worth building at all, in this phase or at all.
2. Whether a derived copy operation is in scope.
3. Whether "new version of the same content" should exist as a concept, and if so how it is created.
4. Whether the Content Library should stay a pure export index, or also allow independent corrections.
5. Whether older exports or older library entries should be preserved, retired, or both.
6. Whether a same-name re-export should be allowed to overwrite the prior export file, or whether the project wants stronger preservation semantics.
7. Whether editing enough to bump the script version should ever be treated as "new content" rather than "edited same content."
8. Whether any content lifecycle event should be allowed to automatically affect requirement, understanding, intent, or authorization status.

## 10. What this proposal does not decide

This proposal does not:

- change any code
- change any schema
- change any data
- alter any existing decision document
- infer Owner approval for any of the above
